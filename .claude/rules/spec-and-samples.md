# 仕様書とサンプルの約束

## 仕様書（docs/spec/scn-format-v0.md）

- 仕様書が正で、パーサは仕様書に従う。実装の都合で仕様と違う動きを入れない。
- 仕様書の「未決事項」に当たる判断は、人に確認してから決める。決めたら、仕様書の該当箇所と `docs/decisions.md` の両方を更新し、未決事項から消す。
- 診断コードを足したら、仕様書の診断表と、それを出すfixtureの両方を用意する。

## サンプル作品（samples/houkago/）

- 実際の作品に近い入力として使う、パーサの主要なテストデータ。ここには、わざと残している警告がある。
  - 本文に無いエンディング（`true_end`）
  - 行き止まりのスタブ（`s014`）
  - 行IDの付いていない行（AIの下書き、`s013b` など）
- テストを通すためにサンプルを書き換えない。サンプルの書き方が仕様と合っていない場合は、どちらを直すべきかを人に確認する。
- 新しい構文を仕様に足したら、サンプルにもその使用例を1つ入れる。

## ゲートの短編（samples/amayadori/）

- フェーズ1のゲートで Claude Code が書いた短編（D052）。プレビューのテストが、選択肢だけで3つのエンディングすべてに着くことを確かめている。`scn check` はエラー・警告・情報とも0件にしておく（段階2の `scn check --stage 2` も0件。T3-2）。
- 作品フォルダの指示書は `CLAUDE.template.md` の名前で置く（`CLAUDE.md` にすると、開発作業中に読み込まれる）。houkago と同じく、テストを通すために書き換えない。

## fixture（crates/scn-core/tests/fixtures/）

- 1つのfixtureでは、1つの構文か1つの診断に絞る。ファイル名は内容が分かるようにする（例：`choice_unclosed.scn`、`dialogue_unknown_speaker.scn`）。
- 正常系と異常系の両方を置く。異常系では、期待する診断コードをファイル先頭のコメントに書く（例：`// expect: E103`）。
