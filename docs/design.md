# ADVシナリオ執筆ツール 設計検討書

2026-10-07 時点（Claude Docs の設計検討書から書き出し）

## 前提と方針

本ツールは「分岐する物語のための、テキストを正とする執筆環境」として、Tauri製のデスクトップアプリで作る。

| 項目 | 決定 |
| --- | --- |
| 実行基盤 | Tauri（Rustコア＋Webフロントエンド） |
| 対象OS | WindowsとmacOS（Linuxは対象外） |
| 縦書き | 編集は横書き、縦書きはプレビューのみ |
| 想定ユーザー | 自分で組み上げる開発者。ただし書き心地は妥協しない |
| 正となるデータ | プロジェクトフォルダ内のテキストファイル |

設計原則は次の6つ。

1. テキストが正。フロー図、一覧、プレビューはすべてテキストから導出し、独自DBに真実を持たない。Git、外部エディタ、grepがそのまま使える。
2. 演出は意図で書く。エンジン固有の表現はエクスポート時のマッピングで解決する。
3. 開発者には全部見せ、書くときは隠せる。同じテキストを「執筆表示」と「ソース表示」で切り替える。
4. 壊れたまま書ける。未定義の参照や未作成の素材でも止めず、警告と仮置きで先へ進める。
5. 形式にバージョンを持たせる。`format_version` と移行処理を最初から用意する。
6. AIが読み書きできる形にする。形式仕様と検証をCLIで公開し、アプリ内のAIも外部のAIエージェントも同じ検証を通す。

## シナリオ形式仕様（ドラフト v0）

> 確定した仕様は `docs/spec/scn-format-v0.md` を正とする。この節は、ドラフト時点の検討の記録として残している（D033）。

1行が1要素の行指向テキストとし、日本語の原稿として自然に読めることと、パーサが曖昧なく読めることを両立させる。拡張子は `.scn` とする。

### ファイルとシーン

- 1ファイルに複数シーンを置ける。章ごとに1ファイルを想定する。
- シーンは `## タイトル #シーンID` で始まる。IDは英数字を推奨し、省略時はツールが採番する。
- 見出しの直後に `---` で囲んだメタ情報（要約、状態、タグ、ルート）を任意で置ける。状態は draft・writing・done・ai-draft のいずれかで、AIが生成したシーンは ai-draft になる。

### 行の種類

| 書き方 | 意味 | 例 |
| --- | --- | --- |
| 行頭が `@` | ディレクティブ（演出・制御） | `@背景 屋上/夕方` |
| `名前「…」` | 台詞 | `灯「やっと来た」` |
| `名前（表示名）「…」` | 表示名を上書きした台詞 | `灯（？？？）「誰？」` |
| `->` で始まる | ジャンプ | `-> s013` |
| 行頭が `//` | コメント（出力しない） | `// 要検討` |
| それ以外 | 地の文 | `　風が強かった。` |
| 空行 | 段落区切り（ADVでは改ページ候補） |  |

台詞の判定は、行頭から最初の「までが登録済みのキャラ名かエイリアスに一致するときだけ行う。一致しなければ地の文として扱い、警告を出す。台詞は閉じ括弧まで複数行にまたがってよいが、空行が来たら打ち切って警告する。『』などの括弧の種類と表示スタイル（心の声、通信など）の対応はプロジェクト設定で決める。

### 文中の記法

- ルビ：`|漢字《かんじ》`（なろう・カクヨムと同じ）。漢字だけの直前なら `|` は省略できる。
- 傍点：`《《強調》》`
- インライン命令：`{w 0.5}` ウェイト、`{p}` 改ページ、`{se ドア}` 文中SE、`{speed 遅}` 文字速度
- 変数の埋め込み：`{=主人公.名前}`。波括弧そのものは `{{` と `}}` で書く。

### ディレクティブ（初期セット）

日本語名と英語名は同じ命令の別名で、どちらで書いてもよい。フォーマッタでどちらかに揃えられる。

| 日本語名 | 英語名 | 引数 |
| --- | --- | --- |
| `@背景` | `@bg` | 背景名、トランジション（任意） |
| `@立ち絵` | `@show` | キャラ、差分、位置（任意） |
| `@退場` | `@hide` | キャラ |
| `@BGM` | `@bgm` | 曲名、または「停止」 |
| `@SE` | `@se` | 効果音名 |
| `@効果` | `@fx` | 揺れ、フラッシュなどの意味名 |
| `@待機` | `@wait` | 秒数 |
| `@設定` | `@set` | 代入式 |
| `@呼出` | `@call` | シーンID（`@return` で戻る） |
| `@選択` | `@choice` | 問いかけ文（`@end` まで） |
| `@if` | `@if` | 条件（`@elif`、`@else`、`@end`） |
| `@エンディング` | `@ending` | エンディング名 |
| `@raw` | `@raw` | エンジン名（`@end` まで） |

プロジェクト設定でマクロを定義できる。たとえば `@回想開始` を「`@fx セピア` と `@BGM 回想`」の組み合わせとして定義したり、エンジンごとの出力を直接割り当てたりする。

### 選択肢と条件分岐

選択肢の書き方は `- 表示文 [if 条件] [-> 飛び先]` とする。選択肢の中身は次の `-` 行か `@end` までで、ジャンプがなければ `@end` の後へ進む。行頭の半角空白は見た目の整形用として無視し、全角空白は本文の字下げとして扱う。インデントに意味を持たせないので、日本語の字下げと衝突しない。

### 式と変数

- 型は真偽、整数、文字列、列挙の4つ。
- 演算子は `==` `!=` `<` `<=` `>` `>=`、`and` `or` `not`、`+` `-` `*` `/`、代入は `=` `+=` `-=`。
- 変数名は `名前空間.名前` の形で、日本語も使える。名前空間を省略すると `flag` になる。キャラIDを名前空間にすると、そのキャラに紐づく値になる。
- 未定義の変数は警告、型の不一致はエラーとして表示する。どちらも編集は止めない。

### 行ID

- 台詞、地の文、選択肢の各行末に `^k3f9` の形でIDを自動で付ける（base36、プロジェクト内で一意）。
- 執筆表示では隠し、ソース表示では薄く表示する。
- 編集しても保持する。行を分割したら前半が元のIDを継ぐ。コピペで重複したら後から現れた方を振り直す。削除したIDは再利用しない。
- ボイス、翻訳、コメント、既読、AIの出自記録は、すべて行IDをキーにする。

### 完全なサンプル

```
## 放課後の屋上 #s012
---
summary: 灯が転校を打ち明けかける
status: draft
route: 共通
---
@背景 屋上/夕方 フェード
@BGM 切ない
@立ち絵 灯 笑顔 左

灯「やっと来た。遅いよ」 ^k3f9
　風が強くて、灯の髪が|乱《みだ》れていた。 ^k3fa
灯「あのね、{w 0.5}話があるんだ」 ^k3fb
@立ち絵 灯 真顔

// ここで転校の話を出すか要検討
@選択 どう答える ^k3fc
- 「ごめん、遅くなって」 ^k3fd
  @設定 灯.好感度 += 1
- 黙ってうなずく if 勇気 >= 2 ^k3fe
  灯「……そういうところ、ずるいよね」 ^k3ff
  -> s014
@end

@if 灯.好感度 >= 3
  灯「やっぱり、君には言っておく」 ^k3fg
  -> s013a
@else
  -> s013b
@end

@raw renpy
  $ renpy.music.set_volume(0.6, channel="music")
@end
```

## プロジェクト構成とデータモデル

プロジェクトは1フォルダで完結させ、ツールが作るキャッシュ以外はすべてGitで管理する前提にする。

```
my-novel/
├─ project.toml       形式バージョン、画面とウィンドウ設定、既定の出力先
├─ CLAUDE.md          AIエージェント向けの指示書
├─ FORMAT.md          形式仕様（ツールが生成・更新）
├─ concept.md         企画書（ログライン、テーマ、エンディング一覧）
├─ style.md           文体の方針と文体見本（AI生成の文脈に必ず入れる）
├─ ideas/             アイデアメモ（1枚1ファイル）
├─ bible/
│  ├─ types/          設定の型定義（character.yaml、foreshadow.yaml など）
│  └─ entries/        エントリ本体（character/akari.md など）
├─ story/             シナリオ（chapter01.scn など）
├─ variables.yaml     変数定義
├─ assets/
│  ├─ catalog.yaml    素材カタログ（意味名からファイルへの対応）
│  └─ files/          実ファイル
├─ export/            エクスポートプロファイル（renpy.yaml など）
├─ ai/                AIタスクの定義と出自記録
├─ layout.json        フロー図のノード座標（本文と分離）
└─ .cache/            索引、要約キャッシュ、サムネイル（Git管理外）
```

### 設定DB

- 型定義はYAMLで書く。項目の型は、短文、長文、数値、真偽、選択（単一・複数）、参照、参照のリスト、素材、日付。
- エントリは「YAMLフロントマター＋Markdown本文」の `.md` ファイルにする。構造化した値はフロントマター、自由記述は本文に置く。
- キャラクター型だけは組み込みで特別扱いする。台詞の話者解決（名前とエイリアス）、立ち絵差分、声優、口調メモ、紐づく変数をここに集める。

```yaml
# bible/types/character.yaml
name: キャラクター
builtin: character
fields:
  - { key: aliases,      label: 呼び名,   type: list<text> }
  - { key: first_person, label: 一人称,   type: text }
  - { key: speech,       label: 口調メモ, type: longtext }
  - { key: want,         label: 欲求,     type: text }
  - { key: conflict,     label: 葛藤,     type: text }
  - { key: org,          label: 所属,     type: ref<organization> }
  - { key: voice,        label: 声優,     type: text }
```

```markdown
---
id: akari
name: 灯
aliases: [あかり, 灯ちゃん]
first_person: わたし
org: kitakaze_high
---
明るく振る舞うが、転校の件を誰にも言えずにいる。
```

### 構造グラフ（プロットとフローの統合）

- プロットカードは、本文が空のシーン（スタブ）として表す。プロットを書くことは、シーン見出し、要約、ジャンプだけを書くことと同じになる。
- グラフの辺は、本文中のジャンプ、選択肢、条件分岐から導出する。フロー図上で辺を引いた場合は、ツールが対応するテキストを書き足す。
- 章はファイル、ルートはシーンメタの `route` で表し、フロー図はこの2つでグループ化して表示する。
- ノード座標は `layout.json` に分け、本文の差分を汚さない。

## アイデアと企画

企画の芯を言葉にしてからプロットへ進む。企画書はプロット系AIタスクすべての最上位の文脈になる。

### 企画書（concept.md）

- プロジェクトに1つだけ置く。構造化した項目はフロントマター、やりたいこと・やらないこと・参考作品は本文に書く。
- 主要キャラの欲求と葛藤は設定DBのキャラクター型に持たせ、企画書ではIDで参照するだけにする。同じ情報を二か所に書かない。
- エンディングを先に決める。各エンディングの `id` はシナリオの `@エンディング` と対応させ、企画と本文の食い違いを検証で出す。

```markdown
---
logline: 転校を言い出せない少女と、屋上でだけ本音を話す主人公の、夏休みまでの三週間
theme: 言わないことは優しさか
tone: 静か、夕方の光、切なさ多め
volume: { chars: 300000, routes: 2 }
main_characters: [akari, tsumugi, hero]
endings:
  - { id: akari_end,   name: 灯エンド, intent: 秘密を受け入れて見送る }
  - { id: tsumugi_end, name: 紬エンド, intent: 灯の不在を経て紬と向き合う }
  - { id: true_end,    name: トゥルー, intent: 両ルートの後、灯が残る理由を見つける }
  - { id: bad_end,     name: すれ違い, intent: 誰にも踏み込めず夏が終わる }
---
夕方の屋上を物語の中心に置く。大きな事件は起こさない。
```

### アイデアメモ（ideas/）

- 1枚1ファイルのMarkdownにする。フロントマターに `status`（未整理・採用・保留・没）、`tags`、昇格先の `promoted_to` を持たせる。
- 採用したメモは、設定エントリ、スタブシーン、伏線エントリのどれかへ昇格できる。元のメモは残し、昇格先へのリンクを記録する。
- 没も消さない。AIの発散タスクの材料として使う。
- 汎用のノートツールやホワイトボードは作らない。メモはObsidianなど外部エディタで書いてもよい。価値はメモ機能そのものではなく、下流のシーンや設定への接続に置く。

```markdown
---
status: 採用
tags: [灯, 屋上]
promoted_to: scene/s012
---
屋上の鍵を持っているのは灯だけ。主人公はなぜ屋上に入れるのか。
```

### 伏線

- 新しい仕組みは作らず、設定DBの型「伏線」で表す。項目は、説明、仕込みシーン（参照のリスト）、回収シーン（参照）。
- 回収先の無い伏線と、仕込みを一度も通らずに回収シーンへ到達できる経路を、検証で警告する。

### 流れとAIの役割

「アイデア → 企画 → 構造（プロット／フロー） → 本文」と進み、本文から構造へは要約で逆流させる。段階の間でAIの役割を変える。

| 段階の間 | AIの役割 |
| --- | --- |
| アイデア → 企画 | 問い返し。企画書の空白や矛盾を質問として返す。メモの分類案を出す |
| 企画 → 構造 | 構成案。エンディングとキャラの葛藤から、ルートの骨格をスタブシーンで提案、または直接生成する |
| 構造 → 本文 | 下書き。スタブシーンの要約から本文の下書きを生成する（AI下書きとして区別） |
| 本文 → 構造 | 要約。本文からシーン要約を作り直し、プロットとのずれを知らせる |

## 変数と検証

変数を宣言制にし、検証を常に走らせることで、フラグ管理の負担を下げる。

```yaml
# variables.yaml
flag.勇気:          { type: int,  default: 0, scope: save }
akari.好感度:        { type: int,  default: 0, scope: save, range: [0, 10] }
akari.転校済み:      { type: bool, default: false, scope: save }
flag.ルート:         { type: enum, values: [共通, 灯, 紬], default: 共通 }
周回.トゥルー解放:    { type: bool, default: false, scope: persistent,
                     desc: 灯と紬の両ルートをクリアすると立つ }
```

- `scope` は、セーブデータ単位の `save` と、周回や既読などゲーム全体で持つ `persistent` の2種類。
- `desc` に用途を書く。検証結果の表示とAIの文脈の両方で使う。
- 変数ごとに、読み書きしている箇所の一覧（参照検索）を出せるようにする。
- エンディングは `@エンディング 名前` で明示し、到達性解析の終点にする。

### 検証項目

| 項目 | 重大度 | 段階 |
| --- | --- | --- |
| 存在しないシーンへのジャンプ | エラー | 1 |
| 型の不一致（真偽に数値を代入、など） | エラー | 1 |
| 未定義の変数・キャラ・素材の参照 | 警告 | 1 |
| 書き込むだけで読まれない変数 | 警告 | 1 |
| 読まれるのに一度も書かれない変数 | 警告 | 1 |
| 開始シーンから到達できないシーン | 警告 | 1 |
| どのエンディングにも続かない行き止まり | 警告 | 1 |
| メッセージウィンドウからのはみ出し | 警告 | 1 |
| 企画書のエンディングと本文の `@エンディング` の食い違い | 警告 | 1 |
| 回収シーンの無い伏線 | 警告 | 1 |
| 決して真にならない条件、選べない選択肢 | 警告 | 2 |
| 仕込みを通らずに回収へ到達できる伏線 | 警告 | 2 |
| エンディングごとの到達条件の一覧 | 情報 | 2 |
| 表記ゆれ、未登録の用語 | 情報 | 2 |

### 到達性解析の進め方

1. 段階1は、条件を無視したグラフ上の到達性だけを見る。安価なので、保存のたびに常時実行する。
2. 段階2は自動巡回にする。開始シーンから全選択肢の組み合わせを実際に実行し、変数状態ごとにメモ化して、状態数には上限を設ける。到達したシーンと選べた選択肢のカバレッジを出す。
3. 整数の取りうる範囲を記号的に解析するかどうかは、段階2の結果を見てから決める。

## アーキテクチャ（Tauri）

真実と重い処理はRustコアに置き、フロントエンドは表示と入力に徹する。コアは言語サーバー（LSP）と同じ形で設計し、将来VS Code拡張からも同じ機能を使えるようにする。

```
フロントエンド（TypeScript・React）
  本文エディタ（CodeMirror 6） / フロー図（xyflow） / 設定フォーム / プレビュー（ADV・縦書き）
        │  Tauri IPC（コマンドとイベント）
Rustコア（プロジェクトの真実を持つ）
  パーサとIR（全機能の共通入力） / 言語サービス / 検証
  ファイル監視 / エクスポーター / AIプロキシ（キー保管・文脈の組み立て）
        │
外部：プロジェクトフォルダ（テキスト＋素材、Git） / エンジン用ファイル / LLM（ローカル・クラウド）
```

フロントとコアはTauriのIPCだけでつながり、ファイル、エンジン出力、LLMとのやり取りはすべてコアが受け持つ。

| 層 | 担当 | 主な技術 |
| --- | --- | --- |
| Rustコア | パース、IR生成、索引、検証、エクスポート、ファイル監視、AI通信、APIキー保管 | 自作パーサ、notify、minijinja、reqwest、keyring |
| 言語サービス | 診断、補完、定義へ移動、参照検索、リネーム、ホバー | tower-lsp（同じ処理をTauriのIPCからも呼ぶ） |
| フロントエンド | エディタ、フロー図、設定フォーム、プレビュー再生 | TypeScript、React、CodeMirror 6、xyflow |

フロントエンドはReactに決定した。xyflowとCodeMirror周りの資産が最も厚いため。

### パーサとIR

- 行指向なので、手書きの再帰下降パーサで十分に書ける。エラー回復を重視し、壊れた行があっても残りは解析を続ける。
- 出力はAST、そこからIRを作る。IRはシーンごとの命令列（Say、Narrate、Show、Hide、Bg、Bgm、Se、Fx、Wait、Set、Choice、If、Jump、Call、Ending、Raw）と、シーン間のグラフで構成する。
- IRはJSONに直列化できるようにし、プレビュー、エクスポーター、外部プラグインの共通入力にする。
- 構文ハイライトはCodeMirror側のLezer文法で軽く行い、意味解析はコアに任せる。二重実装になるが、ハイライトは寛容でよいので差異は問題になりにくい。
- 再パースはファイル単位、索引は差分更新にして、数千シーンの規模でも打鍵ごとの遅延を出さない。

### ファイル監視とTauri固有の方針

- VS Codeなど外部エディタでの同時編集を前提にする。notifyで変更を検知して再読込し、未保存の変更と衝突したらマージ画面を出す。
- ファイルアクセスはフロントから直接行わず、コアのコマンド経由に統一する。Tauriの権限設定を単純に保つため。
- 画像や音声のプレビュー表示はアセットプロトコルで配信する。
- プレビューは別ウィンドウにも出せるようにし、デュアルモニタで本文とプレビューを並べられるようにする。

### コマンドライン（CLI）

コアをCLIとしても配布し、AIエージェントや外部エディタからも同じ検証を使えるようにする。フェーズ1で作る。

| コマンド | 内容 |
| --- | --- |
| `check` | 検証を実行し、問題をファイル、行番号、行IDつきで出力する。JSON出力も選べる |
| `graph` | シーン、辺、条件、変数の読み書きを一覧で出力する。要約の粒度（ルート・章・シーン）を選べる |
| `ir` | IRをJSONで書き出す |

- プロジェクト直下に形式仕様 `FORMAT.md` と、AIエージェント向けの指示書 `CLAUDE.md` を置く。指示書には「編集後は必ず `check` を実行する」「行IDを書き換えない」「プロットはスタブシーンとして書く」を明記する。
- これでClaude Codeが `.scn` や `concept.md` を直接編集し、自分で検証しながらプロット作業を進められる。アプリ内のAI機能は、後から同じ仕組みの上に載せる。

## エディタと書き心地

1つのエディタに「執筆表示」と「ソース表示」を持たせ、開発者が全部を見られることと、書くときに記号が目に入らないことを両立させる。

### 表示モード

- 執筆表示：ディレクティブは小さなチップに畳み、行IDは隠し、ルビは本文の上にルビとして描く。カーソルが乗った行だけ生テキストに戻す（Obsidianのライブプレビューと同じ方式）。
- ソース表示：すべて生テキストで表示し、行IDは薄い色で出す。
- 切り替えはショートカット1つで行い、ファイルごとに状態を記憶する。

### 日本語入力（IME）

- 変換中は補完ポップアップと自動整形を止める。compositionイベントを見て判定する。
- 対象OSはWindowsとmacOSとし、Linuxは対象外とする。TauriはOSごとにWebViewが違う（WindowsはWebView2、macOSはWKWebView）ので、IMEの挙動差に備えて2環境の手動テスト項目を最初から用意する。
- 変換確定のEnterで改行が二重に入る、といった既知の落とし穴は回帰テストにする。

### 入力補助

- `「` を打つと `」` を補う。
- 行頭でキャラ名を打つと候補を出し、確定すると `名前「」` を展開してカーソルを括弧の中へ置く。
- `@` で命令の候補を出す。命令の引数では、背景名、差分名、BGM名を素材カタログから補完する。
- `->` でシーンIDを補完する。存在しないIDなら、その場でスタブシーンの作成を提案する。
- 三点リーダとダッシュの正規化（`...` を `……`、`--` を `――`）は設定で切り替える。
- 地の文の段落頭に全角スペースを自動で入れる。

### 書いている最中に見える情報

- 右ペイン：現在シーンの登場キャラ（口調メモと一人称）、参照している変数、使っている素材。
- ステータスバー：シーンの文字数、ルートの文字数、推定プレイ時間。
- はみ出し警告：メッセージウィンドウの行数と1行の文字数を超える台詞に波線を引く。

### カーソル位置から再生

- 任意の行でショートカットを押すと、プレビューがその行から始まる。
- 変数の状態は、開始シーンからその行までの最短経路を実行した結果で自動的に復元する。手動で上書きもできる。

### キーボード操作

- コマンドパレット、シーンのクイックオープン、定義へ移動（`-> s013` からシーンへ、話者名からキャラ設定へ）、F2でリネーム（キャラ名、シーンID、変数を全体で置換）。
- 集中モード（他のペインを隠す）、タイプライタースクロール、明朝とゴシックの切り替え。

## 素材カタログとプレビュー

素材は意味名で参照し、ファイルがまだ無くても仮素材としてプレビューまで通す。

```yaml
# assets/catalog.yaml
backgrounds:
  屋上/夕方: { file: files/bg/rooftop_evening.png }
  屋上/夜:   {}                      # 未作成（仮素材）
characters:
  akari:
    dir: files/chara/akari/
    expressions:
      笑顔: smile.png
      真顔: neutral.png
      照れ: {}                       # 未作成
bgm:
  切ない: { file: files/bgm/setsunai.ogg, loop: true }
se:
  ドア: {}
```

- 本文で使われた未登録の意味名は、索引が自動で集計する。カタログへの追記はワンクリックで行う。
- 仮素材は、プレビューでは名前入りの色付き矩形、音は無音として扱う。
- 発注リスト：未作成の素材ごとに、種別、名前、使用回数、初出シーン、使用シーン一覧をCSVで出す。立ち絵はキャラ×差分の表で出す。

### ADVプレイヤー

- IRを解釈する小さなTypeScriptランタイムとして作る。再現するのは、背景、立ち絵（左・中・右）、テキストウィンドウ、名前欄、選択肢、BGMとSE、基本のトランジション（フェード）まで。
- 画面サイズとメッセージウィンドウの文字数・行数は `project.toml` で設定し、エクスポート先と揃える。
- デバッグパネル：変数の現在値の表示と編集、バックログ、任意シーンへのジャンプ、選択肢の自動選択。
- 行IDでエディタと同期する。プレビュー中の行をエディタでハイライトし、逆方向にも飛べる。

### 縦書きビュー

- CSSの `writing-mode: vertical-rl` を使う。ルビは `<ruby>`、傍点は `text-emphasis`、2桁の数字は縦中横（`text-combine-upright`）で表現する。
- ルートを選ぶと分岐を解決し、一本道として通読できる。選んだ選択肢は本文中に小さく注記する。
- 1ページあたりの行数と字数、原稿用紙換算の枚数を設定・表示できるようにする。
- WebViewの描画にはOS間の差があるため、縦書きビューは確認用と位置づける。厳密な組版はPDFやEPUBのエクスポートで担う。

## エクスポート

エクスポートは「IRをプロファイルに従って変換する」一方向に限り、生成物を手で直す運用はしない。エンジン側で必要な調整は、`@raw` とマクロで本文側に吸収する。

| 出力 | 段階 | 内容 |
| --- | --- | --- |
| IR（JSON） | 1 | 全情報。自作エンジンや独自変換の入力 |
| 台本（CSV・Excel） | 1 | 行ID、シーン、キャラ、台詞、直前の地の文、ボイスファイル名、備考 |
| プレーンテキスト | 1 | ルート単位の通読用。ルビはなろう・カクヨム記法 |
| Ren'Py（.rpy） | 2 | ラベル、scene・show・play、menu、変数、Character定義 |
| ティラノスクリプト（.ks） | 3 | ラベル、bg・chara\_show・playbgm、glink、変数 |
| 宴（Excel） | 3 | 表形式のシナリオシート |
| EPUB・縦書きPDF | 3 | 小説としての配布用 |

### プロファイルと変換例（Ren'Py）

プロファイルには、意味名からエンジン側の名前への対応、位置やトランジションの対応、ボイスの命名規則を書く。変数名やキャラIDは、エンジンで安全な英数字に変換する対応表もここに持たせる。

```yaml
# export/renpy.yaml
target: renpy
images:
  背景:   "bg {file_stem}"
  立ち絵: "{char_id} {expr_stem}"
positions:   { 左: left, 中: center, 右: right }
transitions: { フェード: fade, 即時: None }
fx:          { 揺れ: "with vpunch" }
voice:       { pattern: "voice/{char_id}_{line_id}.ogg" }
```

シナリオ形式のサンプル冒頭は、次のように出力される想定。

```
label s012:
    scene bg rooftop_evening with fade
    play music "bgm/setsunai.ogg"
    show akari smile at left
    voice "voice/akari_k3f9.ogg"
    akari "やっと来た。遅いよ"
    "風が強くて、灯の髪が{rb}乱{/rb}{rt}みだ{/rt}れていた。"
```

### ボイスと台本

- ボイスファイル名は既定で `キャラID_行ID` にする。行IDは本文を直しても変わらないので、収録済みの音声との対応が崩れない。
- 台本を出力した時点の各行の本文ハッシュを記録しておき、収録後に台詞が変わった行を「再収録候補」として一覧にする。
- `@raw renpy` のような生コードは、対象エンジンへの出力時だけ書き出し、それ以外では警告つきで読み飛ばす。

### プラグイン

- 単純なテキスト形式は、minijinjaのテンプレートだけで出力を定義できるようにする。
- それで足りない場合は外部コマンド型にする。プロファイルに `command: python tools/my_export.py` のように書くと、ツールがIRのJSONを標準入力で渡し、コマンドが出力先へファイルを書く。言語を問わず書けるので、開発者向けとして最も柔軟。

## AI支援

AIは設定と構造を知っている共作者とする。スタブや未作成のルートなど空いている部分には直接生成でき、人が書いた行の変更は差分の提案として扱う。関わり方はタスクごとに選び、生成物はすべてAI下書きとして区別し、出自を記録する。

### 関わり方の段階

| 段階 | level | 内容 | 例 |
| --- | --- | --- | --- |
| 指摘 | `review` | 読んで問題を返すだけ | 口調チェック、設定矛盾チェック |
| 提案 | `propose` | 差分や提案ノードを出し、人が単位ごとに採用する | 既存の行の言い換え、分岐案 |
| 生成 | `generate` | スタブや空きに直接書き込み、人はまとめて確認する | スタブの本文を下書き、ルートの骨格を作る |
| 自律 | `auto` | 生成、検証、自己修正を、条件を満たすまで繰り返す | 灯ルート第2章を下書きまで仕上げる |

- どの段階でも、人が書いた行（出自が「人」または「AI生成を人が修正」の行）は直接変更しない。変更が必要なら提案として出す。
- 自律はCLIとClaude Codeの組み合わせでフェーズ1から使える。アプリ内の「AI実行」画面はフェーズ3で作る。

### 生成の進め方

- 生成物を区別する。AIが作ったシーンはメタ情報の状態を `ai-draft` にし、フロー図とエディタで色を変える。プレビューとエクスポートでは、AI下書きを含めるかを選べる。
- 大きな実行はGitのブランチ（`ai/<タスク名>-<日付>` など）で行い、確認してから取り込む。
- 上から下へ生成する。「企画 → スタブ（要約と分岐） → 展開メモ → 本文」の順に降り、各段で `check` を通す。いきなり長い本文を書かせない。
- 文体見本を持たせる。`style.md` に文体の方針と、自分で書いた見本の文章を置き、生成タスクの文脈に必ず入れる。
- 生成後に自動で点検する。`check` と、口調・設定矛盾のAIレビューを走らせ、直せるものは直してから報告させる。
- 1回の実行に、トークン数と反復回数の上限を設ける。

```yaml
# ai/draft_route.yaml
name: ルートを下書きまで仕上げる
level: auto
model: cloud
context: [concept, style, route_summaries, characters, variables]
scope: empty_only        # スタブと空きにだけ書き込む
branch: ai/{task}-{date}
checks: [check, tone_check, setting_check]
max_iterations: 3
budget: { tokens: 400000 }
```

### 接続

- Rustコアに共通のインターフェースを置く。OpenAI互換APIを基本のアダプタにして、Ollama、LM Studio、llama.cppサーバー、互換APIを持つクラウドをまとめて扱う。互換でないサービスはネイティブのアダプタで足す。
- APIキーはOSのキーチェーンに保存し、フロントエンドには渡さない。
- 既定はローカル接続にする。クラウドへの送信はプロバイダごとに明示的に有効化し、送信内容を事前に確認できるようにする。

### 文脈の組み立て

- 渡すのは、現在シーンの本文、登場キャラのエントリ（口調メモと一人称）、言及された用語、関係する変数の定義、前のシーンまでの要約。
- シーン要約はシーン単位でキャッシュし、本文が変わったら作り直す。
- 文脈長が足りないときに削る順番を決めておく（前シーン要約、用語、キャラ詳細の順に削る、など）。ローカルLLMの短い文脈でも動くことを前提にする。

### AIタスクのテンプレート化

- `ai/` フォルダにタスクを1ファイルずつ置き、渡す文脈、プロンプト、出力形式（指摘リストか差分か）を書く。
- 組み込みタスクは、設定矛盾チェック、口調チェック、表記ゆれと誤字、シーン要約、分岐の薄さの指摘、言い換え候補、スタブの本文生成、ルート骨格の生成、章単位の自律生成。各タスクに関わり方の段階（level）を書く。
- 開発者がプロンプトを直接編集・追加できることを、このツールの強みにする。

```yaml
# ai/tone_check.yaml
name: 口調チェック
context: [scene, characters.speech, characters.first_person]
output: findings        # findings か diff
prompt: |
  以下のシーンの台詞が、各キャラの口調メモと一人称に沿っているか確認し、
  外れている行を行IDつきで指摘してください。
```

### 出力の扱いと出自の記録

- 指摘は行IDつきで返させ、エディタ上に注釈として出す。
- 人が書いた行への書き換えはCodeMirrorの差分表示で見せ、行ごとに採用か却下を選ぶ。
- AIが書いた行と採用した行は `ai/provenance.jsonl` に、行ID、出自（AI生成・AI生成を人が修正・人）、タスク名、モデル名、日時を記録する。人がAI生成の行を編集したら、出自を自動で「AI生成を人が修正」に変える。AI由来の行を後から一覧・出力でき、賞や公募の申告にも使える。

### プロット／フローへのAI支援

プロットはスタブシーンなので、AIの提案は本文と同じくシナリオ形式の差分として扱える。役割を5つに分ける。

| 役割 | 内容 | 出力の形 |
| --- | --- | --- |
| 発散 | 選択肢の先や分岐点の候補を、2〜3通りのスタブシーンで提案する | 提案ノード |
| 生成 | エンディングとキャラの葛藤からルートの骨格を作り、スタブを直接追加する。スタブの本文も下書きする | AI下書き |
| レビュー | ルート間の分量差、結果が同じになる選択肢、未回収の伏線、キャラの動機と分岐の食い違いを指摘する | 指摘 |
| 同期 | 本文からシーン要約を作り直し、プロットカードとのずれを知らせる | 差分 |
| 問い返し | 企画書やメモの空白・矛盾を質問として返す | 指摘 |

- 到達性やフラグの整合はコアが計算する。AIには計算結果の説明と修正案だけを任せ、到達可能かどうかを推論させない。
- 提案はフロー図に提案ノード（色の違う点線の仮ノード）として重ね、ノード単位で採用・却下する。採用した時点で検証を通し、出自を記録する。
- 文脈は企画書を最上位に置き、ルート・章・シーンの3段の要約から粒度を選んで組み立てる。要約は `.cache/` にキャッシュする。
- AIタスクの定義にモデルを書けるようにする。行単位のチェックはローカル、構成の提案やレビューはクラウド、と使い分ける。

```yaml
# ai/branch_ideas.yaml
name: 分岐案を出す
model: cloud
context: [concept, route_summaries, scene, variables]
output: proposals       # findings / diff / proposals
prompt: |
  企画書のエンディングとキャラの葛藤を踏まえ、指定シーンの後に置く選択肢と
  その先のスタブシーンを2〜3通り提案してください。
```

プロジェクトをMCPサーバーとして公開し、外部のAIエージェントからシーンや設定を読み書きできるようにする案も、将来の拡張として残す。

## ロードマップ

形式と執筆の核を先に固める。AIによる支援と生成はフェーズ1からCLIとClaude Code経由で始め、アプリ内のAI機能はフェーズ3で載せる。アプリ内AIは形式と行IDに依存するので、先に作ると作り直しになる。

| フェーズ | 名前 | 内容 | ゲート（次へ進む条件） |
| --- | --- | --- | --- |
| 0 | 形式を固める | 形式仕様v0、パーサとIR、Lezerによるハイライト／Reactの土台の試作（CodeMirror 6・xyflow）／WindowsとmacOSでの日本語入力（IME）テスト | サンプルの分岐シーンがパースでき、WindowsとmacOSで日本語入力に支障がない |
| 1 | 執筆の核 | エディタ（執筆表示・ソース表示）、設定DB、変数定義／構造グラフ、検証の段階1、簡易ADVプレビュー／IR・台本の出力、CLI（check・graph・ir）、企画書とメモの規約 | 分岐のある短編1本を、このツールとClaude Codeだけで書き切れる |
| 2 | 制作に使える | 素材カタログと発注リスト、カーソル位置から再生／Ren'Pyエクスポート、縦書きビュー、企画ビューとメモの昇格／外部エディタとの同時編集（監視とマージ） | 書き出したRen'Pyプロジェクトが起動し、最後まで遊べる |
| 3 | 支援と拡張 | アプリ内AI（AI実行画面・生成・提案ノード・レビュー）、出自記録／ティラノ・宴・EPUB、外部コマンド型プラグイン／自動巡回（検証の段階2）、言語サーバー化とVS Code拡張 | — |
| 4 | ローカルLLMと企画・設定の生成（2026-10-09 に人の判断で追加。D080） | タスクの接続先と文脈長を端末で選ぶ、考えるモデルと構造化出力／企画書と設定の下書き、項目ごとの出自記録、自律の前段 | — |

各フェーズはゲートの条件を満たしてから次へ進む。期間は、フェーズ0でパーサを書いた手応えを見てから見積もる。

## 未決事項とリスク

フェーズ0で決着させるべきなのは、WindowsとmacOSでのIMEの挙動確認。残りはサンプル作品を書きながら検証する。

| 項目 | 内容 | 対応案 |
| --- | --- | --- |
| フロントエンドのフレームワーク | Reactに決定 | 解決済み |
| 形式の名称と拡張子 | `.scn` に決定 | 解決済み |
| IMEの挙動差 | WindowsのWebView2とmacOSのWKWebViewで挙動が違う。Linuxは対象外 | フェーズ0で2OSの入力テストを行う |
| 台詞判定の誤検出 | 名前一致方式で足りるか | サンプル作品で誤検出率を確認する |
| 行IDの見た目 | 外部エディタでは行末のIDが見える | VS Code拡張で隠せるまでは許容する |
| 大規模プロジェクトの性能 | 数千シーンで索引更新が打鍵に追いつくか | 合成データでベンチマークする |
