# 決定記録

決めたことを、番号つきで残す。覆すときは新しい番号で記録し、古い項目に「→ Dxxx で変更」と書き足す。書き方は、決定・理由・影響の3点。

## D001 テキストを正とする（2026-10-07）

- 決定：プロジェクトのデータは、フォルダ内のテキストファイルを正とする。フロー図や一覧はテキストから導出し、アプリ独自のDBは索引とキャッシュ（`.cache/`、Git管理外）だけにする。
- 理由：Git、外部エディタ、grep、AIエージェントがそのまま使えるようにするため。
- 影響：フロー図のノード座標は本文と分けて `layout.json` に置く。

## D002 Tauriで作る（2026-10-07）

- 決定：デスクトップアプリをTauriで作る。解析・検証・入出力はRustコア、表示と入力はWebフロントエンドに分ける。
- 理由：Rustのパーサを、アプリ・CLI・将来の言語サーバーで共有するため。
- 影響：フロントから直接ファイルを読まず、コアのコマンド経由にする。

## D003 フロントエンドはReact、CodeMirror 6、xyflow（2026-10-07）

- 決定：UIはReactとTypeScript、本文エディタはCodeMirror 6、フロー図はxyflow（React Flow）で作る。
- 理由：エディタとグラフ表示の資産が最も厚い組み合わせのため。
- 影響：UIコンポーネント集は使わず、`docs/ui/` のデザイントークンをCSS変数にする。

## D004 対象OSはWindowsとmacOS（2026-10-07）

- 決定：WindowsとmacOSを対象にする。Linuxは対象外。
- 理由：検証できる環境がないため。
- 影響：IMEのテストは2OSで行う（`docs/plan/ime-test.md`）。

## D005 縦書きはプレビューだけ（2026-10-07）

- 決定：編集は横書きで行い、縦書きはプレビューで確認する。厳密な組版はPDF・EPUBの出力で行う。
- 理由：縦書きの編集はWebViewのエディタでは実装と保守の負担が大きいため。

## D006 拡張子は .scn（2026-10-07）

- 決定：シナリオファイルの拡張子を `.scn` にする。

## D007 演出は意味名で書く（2026-10-07）

- 決定：本文には意味名（`@背景 屋上/夕方`）を書き、ファイルやエンジンの命令への対応はエクスポートのプロファイルで決める。
- 理由：複数のエンジンへ出力でき、素材が無くても書き進められるようにするため。
- 影響：素材カタログに無い意味名は、仮素材として扱う。

## D008 行IDを最初から持つ（2026-10-07）

- 決定：台詞・地の文・選択肢に、不変の行ID（`^k3f9`）を付ける。パーサは付与せず、整形コマンドとエディタが付与する。
- 理由：ボイス、翻訳、コメント、既読、AIの出自記録がすべて行に紐づくため。後から入れるのは難しい。

## D009 エクスポートは一方向（2026-10-07）

- 決定：エンジン側で手直ししたファイルを取り込み直す機能は作らない。エンジン固有の調整は `@raw` とマクロで本文側に持つ。

## D010 プロットとフローを1つの構造グラフにする（2026-10-07）

- 決定：プロットカードは本文の無いシーン（スタブ）として表し、フロー図は本文のジャンプ・選択肢・分岐から導出する。
- 理由：プロットと本文のずれをツールで検出できるようにするため。

## D011 AIは共作者（2026-10-07）

- 決定：AIの関わり方を、指摘・提案・生成・自律の4段階からタスクごとに選ぶ。どの段階でも、人が書いた行は直接書き換えず、提案として出す。AIの生成物は `ai-draft` として区別し、行ごとに出自（`ai` / `ai-edited` / `human`）を記録する。
- 理由：生成の自由度を最大にしつつ、人の文章が知らないうちに変わる事故を防ぐため。
- 影響：大きな生成はGitのブランチで行い、確認してから取り込む。

## D012 CLIを早く用意する（2026-10-07）

- 決定：コアをCLI（`scn`）としても配布する。フェーズ0では開発用の `parse` と `ir`、フェーズ1で `check`・`graph`・`ir` をそろえる。
- 理由：アプリ内のAI機能より先に、Claude CodeなどのAIエージェントが本文を編集し、自分で検証できるようにするため。

## D013 企画書とアイデアメモを持つ（2026-10-07）

- 決定：`concept.md`（企画書）と `ideas/`（アイデアメモ）をプロジェクトに置く。キャラの欲求と葛藤は設定DBに持ち、企画書からはIDで参照する。
- 理由：プロット系AIの最上位の文脈にするため。断片を早く構造に押し込まないため。

## D014 伏線は設定DBの型で表す（2026-10-07）

- 決定：伏線のための専用の仕組みは作らず、設定DBの型「伏線」（仕込み・回収のシーン参照）で表す。

## D015 ツール名は仮称 scn-studio（2026-10-07）

- 決定：リポジトリ名とアプリ名は、正式名が決まるまで `scn-studio` とする。CLIのコマンド名は `scn`。

## D016 選択肢の条件は素の ` if 式` で書く（2026-10-07）

- 決定：選択肢の行は `- 表示文 [if 式] [-> シーンID] [^行ID]` とし、条件を括弧で囲まない。行の右から順に、行ID、最後の ` -> `、最後の ` if ` を切り出す。
- 理由：打つ量が少なく、原稿として読みやすい。設計書・画面モック・サンプルがすでにこの形で、書き換えが要らない。
- 影響：表示文に半角の ` if ` や ` -> ` を含めると、最後のものが条件やジャンプとして切り出される（英語の表示文では E601 になりうる）。

## D017 シーンの終わりでは止まり、省略記法は設けない（2026-10-07）

- 決定：シーンの終わりで、暗黙に次のシーンへ進まない。「次のシーン」を表す省略記法（`-> 次` など）も設けない。
- 理由：流れが本文の記述だけで決まり、シーンを並べ替えても変わらない。行き止まり（W503）を検出でき、スタブで構造を表す決定（D010）と合う。
- 影響：一本道の章でも `-> シーンID` を書く。手間はエディタの補完で軽くする。省略記法は、後から足しても既存の原稿を壊さない。

## D018 章見出しはファイルの先頭に任意で1つ（2026-10-07）

- 決定：章見出し（`# ` の行）は、ファイルの先頭（空行とコメントを除く）に任意で1つだけ置ける。先頭以外にある `# ` の行は、W112 を出して地の文として扱う。それが最初のシーンより前にあれば、W101 も出す。
- 理由：「1ファイル＝1章」の想定と合う。章の区切りのつもりで書いた行が、黙って本文に混ざるのを防ぐ。
- 影響：診断 W112 を加えた。

## D019 シーンIDとエンディングIDは英数字と `_`（2026-10-07）

- 決定：シーンIDとエンディングIDは、英数字（`A-Z`、`a-z`、`0-9`）と `_` の1文字以上で書く。大文字と小文字を区別する。形が崩れていれば E111 を出し、見出しはIDの無いものとして扱う（W107 は重ねて出さない）。
- 理由：IMEを切り替えずに打て、全角と半角の取り違えが起きない（文字列は正規化しない約束のため、見た目が同じ別IDが生まれうる）。エンジンのラベルやファイル名にそのまま使える。
- 影響：診断 E111 を加えた。見出しのタイトルは日本語で書ける。

## D020 変数の名前空間に、キャラのID・名前・呼び名を使える（2026-10-07）

- 決定：変数の名前空間がキャラクターのID・名前・呼び名に一致すれば、キャラクターIDにそろえる（`灯.好感度` は `akari.好感度`）。照合は台詞の話者と同じく、ID、名前、呼び名の順に行い、同じ段で2人以上に一致したら解決できないものとする。
- 理由：台詞と同じ感覚で書ける。サンプルの書き方をそのまま使える。
- 影響：「先生」のような一般的な呼び名も、そのキャラの名前空間になる。呼び名を決めるときに気をつける。

## D021 列挙の値は文字列で書く（2026-10-07）

- 決定：列挙型の変数の値は、文字列で書く（`flag.ルート == "灯"`、`@設定 flag.ルート = "灯"`）。宣言の `values` に無い値は E603。
- 理由：変数名と見分けが付き、構文解析だけで式の形が決まる。ハイライトでも区別できる。
- 影響：IMEが `"` を全角の `”` にすると E601 になる。

## D022 未登録の話者は地の文にし、モブも設定DBに登録する（2026-10-07）

- 決定：台詞候補の話者名は、空白（半角空白、タブ、全角空白）と括弧を含まない1〜20文字とする。話者を解決できないとき、行全体が閉じ括弧で終われば W202 を出して地の文として扱い、閉じ括弧の後に文が続けば診断なしで地の文として扱う。モブも設定DBにキャラクターとして登録する。
- 理由：台詞の話者が必ずキャラクターIDになり、ボイスや台本で扱いやすい。設計書の方針（一致しなければ地の文）と同じ。
- 影響：モブごとに登録の手間がかかる。台詞の形をした地の文は、行頭の `\` で判定を止められる（D027）。

## D023 行IDは4〜12文字を受け付け、6文字で作る（2026-10-07）

- 決定：行IDは `[0-9a-z]` の4〜12文字を受け付け、新しいIDは6文字で作る。行末の「半角空白、`^`、英数字」を行IDの候補とし、形が合わなければ（大文字を含む、長さが合わない）E304 を出す。そのとき候補は本文から取り除き、I302 は出さない。`^_^` のように英数字以外を含むものは本文の一部にする。
- 理由：サンプルは4文字のIDで書かれており、行IDは変えない原則（設計の原則5）があるため、4文字を受け付ける必要がある。新しいIDは6文字にして重なりにくくする。
- 影響：なし（現案どおり）。

## D024 空行は、本文に挟まれたときだけ段落の区切りにする（2026-10-07）

- 決定：同じブロックの中で、前後を台詞か地の文の行に挟まれた空行だけを、IRの `break` にする。間のコメントは飛ばして判定し、連続する空行は1つにまとめる。ディレクティブ、ジャンプ、選択肢の行、ブロックの前後にある空行は、見た目の整形として捨てる。
- 理由：サンプルでは、空行は演出やブロックの前後を見やすくするために使われている。それを区切りにすると、IRに意味の無い `break` が増える。本文の間の空行は、小説の体裁での出力や改ページの候補として残す。
- 影響：`break` の出力のしかたは出力プロファイルで決める。空行が閉じていない台詞を打ち切る働き（E201）は変わらない。

## D025 `@raw` の中は、共通の字下げだけを取り除く（2026-10-07）

- 決定：`@raw` ブロック内の空でない行に共通する行頭の空白（文字どおり共通な部分）だけを取り除き、それより深い字下げは保ってIRへ渡す。
- 理由：行頭の半角空白は見た目のためという `.scn` の約束と合い、ブロックを選択肢の中に移してもIRが変わらない。Ren'Pyのように字下げに意味がある言語でも、相対的な字下げは保たれる。
- 影響：エクスポーターは、出力先の文脈に合わせて字下げを足すだけでよい。

## D026 制御の命令は英語名だけ、引数のキーワードは日英の別名（2026-10-07）

- 決定：`@if`、`@elif`、`@else`、`@raw`、`@end` には日本語名を設けない。引数のキーワード（位置の `左`＝`left`、`中`＝`center`、`右`＝`right`、`@BGM` の `停止`＝`stop`）は日英の別名とし、IRでは英語の値にそろえる。命令名は大文字と小文字を区別する（`@Bgm` は W401）。
- 理由：ブロックの境目が目立ち、IMEを切り替えずに打てる。「終わり・終り・おわり」のような表記ゆれを生まない。
- 影響：なし（現案どおり）。

## D027 行頭の `\` は、どの文字の前でも使える（2026-10-07）

- 決定：行頭の `\` は、続く文字が何でも取り除き、残りを地の文として分類する。`\` で始まる地の文は `\\` と書く。
- 理由：規則が1つで覚えやすい。記号のエスケープに加え、台詞の形をした地の文も書ける。
- 影響：現案の5種（`\@`、`\-`、`\/`、`\#`、`\\`）は、この規則の一部になる。

## D028 台詞の括弧は project.toml で決め、既定は「」だけ（2026-10-07）

- 決定：台詞に使える括弧と表示スタイルは、`project.toml` の `[dialogue.brackets]` で決める。この節を書くとその一覧が既定を置き換え、書かなければ「」（`normal`）だけを使う。表示スタイルの値はコアでは解釈せず、IRの台詞に `style` として渡す。キーは、開き括弧と閉じ括弧が互いに違う文字の2文字。プロジェクトの外で1ファイルだけを解析するときは、既定の「」だけを使う。
- 理由：『』は書名にも使うので、既定に入れると W202 の誤警告が出やすい。見せ方（心の声、通信など）は作品ごとに違うので、値を固定しない。
- 影響：IRの `say` に `style` を持たせる（形はT0-4で確定）。

## D029 T0-2で決めた細部の解釈（2026-10-07）

- 決定：仕様書に書かれていなかった次の解釈を決めた。
  - メタ情報で同じキーが2回以上あれば、後の値を使い、W113 を出す。
  - 選択肢の行に `-> シーンID` を書いたときは、中身を実行してから飛ぶ（中身の最後にジャンプを書いたのと同じ）。
  - `@選択` の行と最初の選択肢の行の間に置けるのは、空行とコメントだけ。ほかの行には E402 を出して読み飛ばす。→ D031 で変更（`@end` を除く）
  - 2つ目の `@else` と、`@else` の後の `@elif` は E104。
  - `@end` で閉じていないブロックは、次のシーン見出し、またはファイルの終わりで閉じたものとみなす（E103）。→ D030 で変更（`@raw` の中では、行頭に空白の無い `## ` の行）
  - 式の変数名は数字で始められない（`1日目` は E601）。`and`、`or`、`not`、`true`、`false` は名前に使えない。整数は半角の数字で書く。
- 理由：構文解析（T0-3）と意味解析（T0-4）の実装で必ず当たる解釈を、先に決めておくため。
- 影響：診断 W113 を加えた。E402 の内容に「最初の選択肢より前の行」を加えた。

## D030 `@raw` の中の行は解析しない（2026-10-07）

- 決定：`@raw` の中の行には、行IDの切り出し、行頭の空白の読み飛ばし、分類を行わない。探すのは、前後の空白を除くと `@end` だけになる行だけ。それより前に行頭に空白の無い `## ` の行が来たら、`@end` の閉じ忘れとみなし、E103 を出してその手前で閉じる。どちらも無ければファイルの終わりで閉じる。
- 理由：生コードを1文字も変えずに渡すため（`## ` で始まるRen'Pyのコメントや、`^` を含む式を壊さない）。閉じ忘れても、次のシーンから先が生コードに飲み込まれないようにするため。
- 影響：D029 の「閉じていないブロックは次のシーン見出しで閉じる」は、`@raw` の中では「行頭に空白の無い `## ` の行」と読む。`## ` で始まる行を中身に書くときは字下げする（共通の字下げは D025 で取り除かれる）。

## D031 構文の細部（2回目）（2026-10-07）

- 決定：`plan-reviewer` の確認で見つかった、構文解析の解釈を決めた。
  - 閉じていない台詞は、空行、シーン見出し、ディレクティブ、選択肢の行、ジャンプの行、ファイルの終わりの直前で終える（E201）。途中のコメントの行は飛ばす。
  - 選択肢の行は「`-` の後に半角空白が続くか、`-` だけ」の行。` if ` と ` -> ` の前の空白は、`-` の後の空白と兼ねてよい（`- -> s014` は表示文が空で E402）。
  - `@選択` の直後の `@end` は E402 の対象にせず、E106 だけを出す。
  - `@選択`（問いかけ文）、`@設定`、`@if`、`@elif` は、行の残り全体を1つの引数として読む。
  - `@立ち絵` の引数が3つで3つ目が位置のキーワードでなければ、トランジションとして読む。引数が4つで3つ目が位置でなければ E402。`@効果` と `@待機` の秒が数でなければ E402。
  - 行IDを持てる行（台詞、地の文、`@選択` の行、選択肢の行）に行IDが無ければ I302。
  - メタ情報の閉じたブロックの中で `キー: 値` の形でない行には E114 を出して読み飛ばす（空行は読み飛ばすだけ）。`---` が閉じていないとき（E102）は、`キー: 値` の形の行が続く間だけをメタ情報とみなす。
- 理由：T0-3の実装で必ず当たる解釈を、先に決めておくため。
- 影響：診断 E114 を加えた。E102 の回復を「次の空行まで」から変えた（本文の行がメタ情報に取り込まれないようにするため）。

## D032 意味解析の細部（2026-10-07）

- 決定：`plan-reviewer` の確認で見つかった、意味解析の解釈を決めた。
  - W502 は枝（シーンの本文、選択肢の中身、`@if`・`@elif`・`@else` のそれぞれの中身）ごとに判定し、ジャンプ、`@エンディング`、`@戻る` の後ろの行に出す。枝を区切る行、空行、コメントには出さない。
  - 素材カタログと照合する（I403）のは、`@背景` の背景名、`@立ち絵` の差分、`@BGM` の曲名、`@SE` と `{se}` の効果音名だけ。トランジションと `@効果` の効果名は照合しない。
  - `@立ち絵` のキャラを解決できない（W404）ときは、差分を照合しない。
  - 宣言されていない変数（W602）には型の検査をしない。E604 を出したときは E603 を重ねない。
- 理由：決めないと、サンプルに意図しない診断が出る（`-> s013a` の直後の `@else` に W502、`フェード` に I403）。同じ誤りに診断を重ねて出さないため。
- 影響：なし（診断の種類は増えない）。

## D033 設計書に注記を足し、サンプルに使用例を2行足す（2026-10-07）

- 決定：`docs/design.md` の形式の節に、確定した仕様は `docs/spec/scn-format-v0.md` を正とする注記を足す（本文はClaude上の元の資料とそろえたまま）。サンプルの `s012` に心の声の台詞（`灯『……やっぱり、言えないかも』 ^k3fh`）を、`s013a` に `@BGM 停止` を足す。
- 理由：設計書の古い記述（「シーンIDは英数字を推奨」など）を正と取り違えないため。サンプルに、表示スタイル `thought` の台詞と、BGMの停止の使用例を入れるため。

## D034 細部（3回目）（2026-10-07）

## D037 開発用CLI `scn` の動き（2026-10-07）

- 決定：T0-5で作った開発用CLIの、計画書に書かれていなかった動きを決めた。
  - `scn parse <file>` は、ファイルのあるディレクトリから上へ `project.toml` を探す。見つかればプロジェクト全体で解析し（設定DB・変数・素材カタログ・ほかのファイルのシーンを使う）、そのファイルの診断だけを出す。`story/*.scn` でないファイルも、プロジェクトの本文に加えて解析する。見つからなければ、構文解析だけを行う（台詞の括弧は既定の「」だけ）。
  - 診断は `ファイル:行:列 コード メッセージ` の形で標準出力に出す。ファイルは引数に書かれたとおりのパス、行と列は1から数え、列は文字の数（先頭のBOMは数えない）。件数のまとめは標準エラーに出す。`--json` では、IRの診断に行と列（`line`、`column`、`end_line`、`end_column`）を足したものの配列を出す。
  - `scn ir <dir>` は、IRを整形したJSONで標準出力に出し、ほかには何も出さない。
  - 終了コードは、出した診断（`parse` はそのファイル、`ir` はプロジェクト全体）にエラー（E）があれば1。設定ファイルが読めないときは、`parse` でも2（→ D042 で変更：設定ファイルの誤りは診断になり、`parse` も設定ファイルの診断を出す）。出力先のパイプが閉じたときは、黙って書くのをやめ、終了コードは診断に従う（`scn parse … | head` でもエラーを見落とさない）。
  - 行と列の計算（`LineIndex`）は `scn-core` に置き、CLIとテストで同じものを使う。
  - 作品フォルダで `scn` として使うときは、ツールのリポジトリで `cargo install --path crates/scn-cli` を実行して入れる（人の判断）。
  - 作品フォルダのAIエージェント向けの手順には、ファイルごとの `scn parse` に加えて、最後に `scn ir . > /dev/null` の終了コードで作品全体のエラーを確かめる手順を入れる（人の判断）。
- 理由：作品フォルダの中で、AIエージェントが書いたファイルだけを手早く確かめられるようにする。引数のとおりのパスと `行:列` は、エディタやターミナルでそのまま開ける。終了コードで、エラーの有無だけを見分けられる。
- 影響：`CLAUDE.md` のコマンドの節と、`samples/houkago/CLAUDE.template.md` の検証の手順を、実際のコマンドに合わせた。

## D041 閉じ括弧の後ろがインライン命令だけの台詞と、行IDの付与（2026-10-07）

- 決定：
  - 閉じ括弧の後ろが、インライン命令（`{w …}`・`{p}`・`{se …}`・`{speed …}`）と空白だけの行（`灯「またね」{p}`）は、後ろに文が続かないものとし、台詞にする（人の判断）。命令は台詞の本文の末尾に付け、間の空白は捨てる。変数の埋め込み、ルビ、傍点は文を作るので、それだけでも文が続くものとする。命令として読めないもの（W405）は文字なので、文が続くものとする。話者を解決できなければ、閉じ括弧で終わる行と同じく W202 を出して地の文にする。Lezer文法も同じ規則で見分ける。仕様書6節を補った。サンプルにも使用例を1つ入れた（chapter02 の `灯「またね、湊。{p}……またね」{w 1} ^b4a1`。人の判断）。
  - IDの無いシーン見出し（W107）に、`scn fmt` はシーンIDを付けない（人の判断）。シーンIDはジャンプに書く名前なので、人かAIエージェントが付ける。エディタの補助（空いている番号の提案など）はT1-8で決める。仕様書5節の「IDはフェーズ1の整形コマンドで付ける」を改めた。
  - `scn fmt` が行IDを付けるのは、I302 の出る行すべて（人の判断）。`status` が `ai-draft` のシーンの行にも付ける。形の合わない候補のある行（E304）には付けない。
  - 付ける場所は、その行の末尾（改行の直前。行末の空白があれば、その後ろ）。` ^` と新しいIDを足すだけで、ほかのバイトは変えない。新しいIDは6文字の `[0-9a-z]` で、本文にある既存のID（行IDを持てない行に付いたものや、形の合わないものを含む）と重ねない。乱数はSplitMix64を自前で持ち、種をプロセスごとに変わる値（`RandomState`）と時刻から取る（依存を足さない）。仕様書9節を補った。
  - `scn fmt <project-dir>` は行IDを付け、付けた行を `ファイル:行:列 ^ID` の形で出す（`--json` でJSON）。`--check` は書き換えずに付ける行を出し、あれば終了コード1。本文のエラーでは止めず、終了コードも1にしない（壊れたまま書ける）。整形（字下げや空白の調整）はしない。付けた行は、ファイルを1つ書くたびに出す。途中のファイルで書き込みに失敗しても、書き終えたファイルの分は出してから終了コード2で終える（出自の記録から漏らさないため）。出力のパスは、`parse` と同じく実行した場所から開けるよう、引数のフォルダにプロジェクトの中の相対パスをつなげる（引数が `.` なら相対パスだけ）。
  - ファイルの書き換えはコアの `write_source` で行う（T1-6の保存でも使う）。同じフォルダに一時ファイルを書き、ディスクへ書き出して（`sync_all`）から置き換えるので、途中でプロセスが止まっても元のファイルは壊れない（電源断で置き換えそのものが残るかまでは保証しない）。読み取り専用のファイルは、OSによらず書き換えずにエラーにする。シンボリックリンクは、リンクを残したまま、リンク先を書き換える。
  - 外部のAIエージェント（Claude Codeなど）が書いた行の出自は、エージェントが自分で記録する（人の判断）。書き始める前に `scn fmt` で既存の行に行IDを付けておき、書き終えたら `scn fmt` を実行して、付いた行IDのうち自分が書いた行のものを `ai/provenance.jsonl` に書き足す。形は `{"line": 行ID, "origin": "ai", "task": "external:<エージェント名>", "model": モデル名, "at": 日時}`。`task` は、AIタスクの定義（`ai/*.yaml`）から実行したときはその名前、外部のエージェントが書いたときは `external:` で始める。手順は `samples/houkago/CLAUDE.template.md` に書いた。記録を自動で書く仕組みは、出自の記録としてフェーズ3で作る。
- 理由：
  - `{p}` や `{w}` は台詞の表示の後ろの間（ま）で、台詞の外に書くのが自然。地の文にすると、話者の解決も表示スタイルも失われる。文を作る記法は、地の文の体裁（`彼は「行こう」と言った。`）と区別がつかないので、今の規則のままにする。
  - 行IDは、AIの出自の記録、コメント、翻訳が頼るので、AI下書きの行にも要る。
  - 行IDを足すだけにすれば、本文を黙って変えない（CLAUDE.mdの「コードの約束」）。
  - 出自を行ごとに残しておかないと、人が手を入れて `status` を変えた後に、どの行がAIのものか分からなくなる。自動で書く仕組みを先回りして作らず、エージェントの手順で足りるようにした。
- 影響：仕様書の5節・6節・9節、`crates/scn-core/tests/fixtures/README.md`、`CLAUDE.md` のコマンドの節、`.claude/rules/rust.md` のモジュールの表（`line_id`）、`samples/houkago/CLAUDE.template.md`、`samples/houkago/story/chapter02.scn`（使用例）、`docs/plan/phase1.md`（T1-5の出自の記録の形、T1-8のシーンIDの補助）を更新した。`provenance.jsonl` の形と `task` の書き方は、T1-5で作品フォルダの規約の文書にまとめる。

## D045 アプリの骨格、保存、外部の変更の取り込み（2026-10-08）

- 決定：
  - 開いている作品フォルダは、コアの `workspace::Workspace` が持つ（保存していない本文と、ディスクの中身）。アプリ（Tauri）はこれを通して保存し、外部の変更を取り込む。ファイルを読み書きするのはコアだけ。
  - 保存（Ctrl+S／Cmd+S）のときに、そのファイルの行IDの無い行（I302）に行IDを付ける（人の判断。`scn fmt` と同じ規則）。足した ` ^ID` のほかは、エディタの本文のバイトのまま書く（`write_source`）。付けた行IDは、エディタの本文にも、行末に足すだけの変更で入れる（カーソルを動かさない）。
  - 行IDの付与を止める `project.toml` の誤りは、本文の読み方に関わるもの（`project.toml` そのものを読めない E801、`format_version` の E802・E803、`[dialogue]`・`[dialogue.brackets]` の E802）だけにする（人の判断。D042を改める）。`title`・`start_scene`・`[message_window]` の誤りでは台詞の読み方が変わらないので、止めない。`scn fmt` も同じ（`Project::has_reading_errors`）。
  - 保存は1つずつ行う。保存を待つ間（約50ミリ秒）に打った文字は消さず、保存で付いた行IDを、保存したときにあった行の今の行末に足す（改行して足した行には付けない。行が消されたか空になっていれば足さない）。今の行がすでに行IDで終わっていれば（保存を待つ間に行IDのある行と結合した、行IDごと貼り付けた）足さない（2つ並べると、前の行IDが本文の文字列として黙って残るため）。付いた行IDを捨てると、次の保存で同じ行に別の行IDが付き、ディスクに書いた行IDが変わってしまうため（設計の原則5）。保存を待つ間に別のファイルへ切り替えたときも、そのファイルの最後の本文に入れてコアへ送る。保存を待つ間にもう一度保存のキーが押されたら、終わってからもう一度保存する。
  - 変換中は保存しない。保存のキーが押されていれば、変換が終わってから保存する。変換中は、解析の結果・外部の変更の知らせ・保存の結果で表示を変えず、変換が終わってから反映する（D039）。
  - 改行の種類が混ざった本文（`\r\n` と `\n`、または `\r` だけの改行）は、エディタが改行を1種類しか持てないので、多いほうにそろえて読み込み、「保存するとそろえる」と知らせる（人の判断）。編集しなければ未保存にしない（ファイルは変わらない）。外部の変更で改行の種類が変わったときは、エディタの状態を作り直す。
  - ファイルの監視は `notify` で行い、知らせを150ミリ秒まとめてから取り込む。本文のファイルは、ディスクの中身が知っている中身と同じなら何もしない（自分で保存したときの知らせ）。保存していない変更が無ければ読み込み直し、あれば「読み込み直す」か「自分の変更を残す」かを選ばせる（マージの画面はフェーズ2）。外で足された章は加え、消された章は除く（保存していない変更があれば、「閉じる」か「自分の変更を残す」（保存で作り直す）かを選ばせる）。設定ファイル（`project.toml`、変数、素材カタログ、設定DB、企画書）が変われば、設定を読み直す（保存していない本文は残す）。フロントでは、まだコアへ送っていない編集がある（入力の後200ミリ秒以内）のにコアが読み込み直したとき・閉じたときも、選ばせる（コアが閉じたファイルは「自分の変更を残す」で開き直す）。
  - 保存の前に、ディスクの中身が知っている中身と同じかを確かめる。違えば（監視の知らせが届く前の外部の変更）、上に書かずに衝突にして選ばせる（外の変更を黙って失わないため）。選ぶ前の外の中身が残っているときも同じ。画面は、自分が知っているディスクの中身を保存に添え、コアの知っている中身と違えば（コアが取り込んだ外部の変更の知らせが、まだ画面に届いていない）、これも衝突にする。
  - 読めない本文のファイル（UTF-8でない、読む権限が無い、書いている途中など）は、消されたとは扱わず、取り込まずに知らせる。

## D046 執筆表示とソース表示（2026-10-08）

- 決定：

  - 執筆表示は、行を1行ずつのまま、行ごとの飾りで見せる（人の判断）。モックのように行をまとめたり消したりはしない（どの行にもカーソルで入れるように）。

## D051 台本の出力（2026-10-08）

- 決定：

  - 行IDの無い台詞（形の合わない行IDを含む）は、行は出し、行IDとボイスファイル名を空にして備考に「行IDなし」と書き、数を知らせる（CLI は標準エラー、アプリは画面）。終了コードは変えない。行IDが重なっている台詞（E301）は備考に書く。CLI は、エラーの診断があれば数を標準エラーに出す。

  - 備考：AI下書きのシーン、心の声（`thought`）、ほかの表示スタイル、表示名、文中の効果音、行IDなし。
  - 文字コードは UTF-8（BOM付き）、改行は CRLF、RFC 4180 の引用（Excel で文字化けせずに開け、欄の中の改行も保てる）。
  - 終了コードは `scn ir` と同じ（エラーの診断があれば1、作品フォルダでなければ2）。
  - アプリの「出力」の画面は、保存していない本文も含めて台本を作る（保存していないファイルがあれば知らせる）。CLI はディスクの中身から作る。

  - Ren'Py の `menu` は選べる選択肢が無いと次の文へ進むので、選択肢がすべて条件付きの `@選択` は、どれも選べないときに `menu` の前で行き止まりとして止まる（プレビューと同じ）。選択肢の無い `@選択`（E106）は `menu` を書かずに行き止まりにする（空の `menu` は Ren'Py が読めず、プロジェクト全体が起動しなくなる）。

  - マクロは作らない（W401 の知らないディレクティブは、コメントにして知らせる）。エンジン側の調整は `@raw renpy` で書く。

## D058 外部エディタとの同時編集のマージ（2026-10-08）

- 決定：
  - 保存していない変更があるのに外で本文が変わったら、「読み込み直す」「自分の変更を残す」に加えて「マージする」を選べる（外で消されたときは除く）。マージは元（読み込んだときのディスクの中身）・自分（保存していない変更）・外（外で変わった中身）の3方向で、コアの `merge` が行う。
  - 行の対応は、行IDのある行は行IDで、無い行（とコメントの行）は中身で、Myers の差分で求める（`similar` を足した。小さく定番の差分のクレートで、ほかの依存は無い）。行IDで対応した行は、中身が変わっていても同じ行として扱うので、隣り合う行を自分と外が直してもぶつからない。
  - 元から見た変更（元の行の範囲を新しい行に置き換える）を自分と外で並べ、元の範囲が重なるもの、同じところに行を足したものどうしを「ぶつかり」にする。隣り合うだけの変更は両方を取り込む。両方が同じに変えたもの（改行の違いだけのものも）はぶつからない。行IDのある行が外で消え、自分がその行を直していればぶつかり、直していなければ消す。ファイルの終わりの改行の有無は、行と別に3方向で決める。
  - 行の移動：片方が行IDのある行を（中身を変えずに）動かし、もう片方がその行を直していれば、動かした先に直した中身を置く（元の位置ではぶつけない）。それでも結果に、自分にも外にも無いほど同じ行IDが並べば（両方が動かした、動かして直したなど）、後のものをコメントにして印で囲む（行IDが2つにならない）。
  - ぶつかりは、マージの画面で並べて「自分の変更」「外の変更」「両方」から選ぶ（既定は両方）。両方は、自分の行を残し、外の行は `// ` を付けたコメントにして `// ▼ マージ：外の変更（コメントにして残した）`・`// ▲ マージ` で囲む（外で消されていれば `// ▲ マージ：外の変更では、上の行が消されていた`）。コメントの行からは行IDを読まないので、行IDが2つにならず、解析も壊れない。
  - マージした結果は、保存していない変更として開く（ディスクの中身は外の中身。「自分の変更を残す」と同じ扱い）。保存すると行IDを付けて書く。マージの結果の行は、元・自分・外のどれかの行そのもので、行IDは書き換えない（設計の原則5）。
  - マージの元は、ふつうはコアが知っているディスクの中身（読み込んだときの中身）。知らせの途中の競合（コアが読み込み直した後に、アプリがまだ送っていなかった編集を戻した）と、置き換えを見送ったとき（マージした結果や読み込み直した中身を、エディタに入れる前に打っていた）は、アプリが元を覚えてコアに渡す（コアは、その後にまた外で変わっても、同じ元を使う）。
  - マージの画面に見せたマージには、入力（元・自分・外）の見分け（`token`）を付ける。当てるときに今の入力から作ったマージと照らし、違えば（見せた後に外か自分が変わった）何も変えずに断る。画面を開いている間にそのファイルが外で変わったら、画面を閉じる。
  - `@raw` のブロックの中のぶつかりで「両方」を選ぶと、印のコメントの行が生コードになる（15節。4節の処理をしないため）。マージの画面に、そこでは自分か外を選ぶように書く。改行の種類だけの違いも変更として数える（混ざった改行のファイルは、エディタがそろえるので、ぶつかりが増えることがある）。
  - 差分を求める時間に上限（2秒）を置く。超えたら、最短でない差分（ぶつかりが増えうる）になるだけで、結果は正しい。
  - 設定ファイル：フォームの項目は今のまま（直した項目だけを照らす。D049）。本文（フロントマターの後ろ）は、外でも本文が変わっていれば3方向でマージし、ぶつからなければ書く。ソース表示の衝突では「マージする」で、元・下書き・外をマージした結果を下書きに入れ、ぶつかりは `<<<<<<< 自分の変更`・`=======`・`>>>>>>> 外の変更` の印で囲む。印が残っている間は保存しない。
- 理由：VS Code などで同時に直したときに、どちらかの変更を捨てずに済むようにする（設計検討書「ファイル監視とTauri固有の方針」）。行IDで行を対応させると、台詞を直しながらの同時編集で、ぶつかりが減る。両方を残す既定を、解析を壊さないコメントにしたのは、原則4（壊れたまま書ける）と原則5（行IDが2つにならない）のため。
- 影響：`crates/scn-core/src/merge.rs`（新規）、`workspace.rs`（`merge_view`・`apply_merge`（元と見分けを受け取る）、本文のマージ）、`Cargo.toml`（`similar`）、`app/src-tauri`（`merge_view`・`apply_merge`・`merge_source`）、`app/src/editor/`（`MergePanel.tsx`・`merge.ts` 新規、`ConflictBar.tsx`）、`App.tsx`、`bible/SourceView.tsx`、CSS。

## D061 設定DB・変数・台本の残り：型定義と変数のフォーム、値の検査（W807）、`story/` のサブディレクトリ、台本の Excel 形式と再収録候補、設定ファイルの BOM、`scn ir --compact`（2026-10-08）

- 決定：

  - レビューで決めたこと：変数のフォームは、読み込みで読み飛ばされる宣言（型が無い・読めない、値の無い列挙）になる書き換えを断り、値の無い変数を列挙にするときは値・型の順に書く。範囲の無い変数では、先に入れた片方を覚えて、両方そろったら書く。型定義のフォームは、行末のコメントを残し、並べ替えでは読めない項目を飛ばす。台本の中で重なっている行ID（E301）は、収録の基準にも比較にも使わない。無くなった台詞の行IDも知らせる。読めない下のフォルダは E801。監視でフォルダの知らせを受けたら、その下の章をまとめて調べる（フォルダごと動かしたとき、中のファイルの知らせが来ないことがあるため）。フロー図の章の粒度とパネルは、`story/` からのパスで章を出す。
  - 設定ファイル（YAML、フロントマター）の先頭の BOM は読み飛ばし、アプリの書き換え（フォーム、素材カタログ、名前の変更）では残す（`docs/progress.md` の「フェーズ2へ」。Windows のエディタが付けた BOM で、ファイル全体が E801 にならないように）。

## D066 AIの接続とキーの保管（2026-10-08）

- 決定：
  - コアに `ai` を作る：接続先の解決（`project.toml` の `[ai.<名前>]` に、端末の設定を重ねる）、呼び出し（OpenAI 互換のチャットの補完を基本のアダプタにし、ネイティブのアダプタとして Anthropic の Messages API）、キーの保管（`keyring`。OS のキーチェーン）。HTTP は `reqwest` の同期の呼び出し（`blocking`）で、TLS は OS のもの（`native-tls`。Windows と macOS で別の道具が要らない）。アプリは別のスレッドで呼ぶ。
  - 置き場所：チームで共有するもの（種類、URL、モデル）は作品フォルダの `project.toml` の `[ai.<名前>]`。端末ごとのもの（URL とモデルの上書き、クラウドへの送信の許可）はアプリの設定のフォルダの `ai.toml`。キーは OS のキーチェーン（行き先 `<provider> <base_url>` ごと）。
  - `[ai.*]` の型の誤りは E802（その接続先を読み飛ばす）。知らない `provider` や足りない値は、使うときに知らせる。
  - ストリーミング（SSE）で頼み、返さないサーバーはまとめて読む。タイムアウトはつなぐまで10秒、次のデータまで180秒（全体は区切らない）。取り消しはデータの合間。トークン数は `usage`、無ければ文字数から見積もる（`estimated`）。
  - クラウド（`anthropic` と、ローカル・LAN 以外の OpenAI 互換）へは、端末で許可した行き先にだけ送る。`http://` のクラウドへはキーを送らない（URL は読んだ書き方にそろえてから見分ける）。別の URL へ移るよう返されてもついて行かない（許可していない行き先へキーと本文を送らないため）。知らせる文からキーを取り除く。読めない端末の設定は書き換えない。
  - 既定の接続先は `[ai.local]`（無ければ最初のローカル、無ければ最初の接続先）。
  - アプリ：左端のバーに「環境設定」（接続先ごとに、使う URL とモデル、上書き、キーの保存と削除、クラウドの許可、「接続を試す」（決まった短い問い。クラウドは送る中身を見せて確かめてから送る。取り消せる））。タイトルバーに既定の接続先と、試した結果の印（形でも分ける）。

## D067 AIタスクの定義と文脈の組み立て（2026-10-08）

- 決定：
  - `ai/*.yaml` の形を規約にする（`name`・`level`・`model`・`context`・`output`・`scope`・`branch`・`checks`・`max_iterations`・`budget`・`prompt`）。タスクの名前はファイル名。誤りは設定ファイルの診断（E801・E802。新しいコードは足さない）にし、キーを既定にして続ける。`model` の接続先や `checks` の名前は使うときに確かめる。`output` に `summary`（シーン要約）と `draft`（生成と自律の書き込み）を足し、段階に合わない組み合わせは E802。

## D069 提案と行ごとの採用（2026-10-08）

- 決定：
  - 提案は行IDつきの差分（行ID、今の文、案、理由）。アプリの提案のタスク（`output: diff`）の応答（1行に1つの JSON）と、外部のAIエージェントが置く `ai/proposals/*.md`（フロントマターの `task`・`model`・`at` と、`## ^行ID` ごとの `- 今：`・`- 案：`・`- 理由：`）を、コアの `ai::Proposal` にそろえる。作品フォルダの指示書の手順にもこの形を書いた。
  - 採用は人の操作だけ（原則6）。コアが採用できる行だけを、行頭の字下げと行IDを残して置き換え、その章を保存し（ワークスペースの保存。行IDの付与と ai-edited の記録も同じ）、採用した行の出自を `ai`（タスクとモデル）として書き足す。採用しないとき：行IDが無い・重なっている（ほかの章も、コメントと `@raw` の中は数えない）、複数行の台詞、今の行が提案の「今」と違う、「今」が無い、案が空・改行・行IDを含む、行の種類が変わる、当てた後の章の有効な行IDの集まりが変わるか構文の誤り・警告が増える、もう案と同じ。外部の変更とぶつかったとき・書けなかったときは採用せず、本文を戻す。段落頭の全角空白は、案に無ければ残す（AI が字下げとして落としやすいため）。
  - 差分の見せ方は、CodeMirror の差分の拡張（`@codemirror/merge`）を足さず、コアが `similar` で文字ごとの差分を作り、画面のカードで「今」（削る文字に取り消し線）と「案」（足す文字に下線）を見せる。行ごとに「採用」「却下」「行へ移動」、まとめて「採用できるものをすべて採用」。
  - アプリの提案はアプリの中だけ（指摘と同じ）。`ai/proposals/` の提案はファイルから読み、採用・却下してもファイルは書き換えない（変更の知らせ `proposals` で一覧を読み直す）。
  - 提案ノード（`output: proposals`）は T3-10。
- 理由：設計検討書「関わり方の段階」「出力の扱いと出自の記録」（人が書いた行への書き換えは差分で見せ、行ごとに採用か却下を選ぶ）。行IDを変えないのは原則5。案をそのまま採用した行は AI が書いた文なので `ai` にする（人が後で直せば ai-edited になる）。差分の拡張を足さないのは、採用を行IDと出自の記録で管理するため（エディタの中で直接当てる仕組みは、行IDを守る扱いと合わない）。
- 影響：`crates/scn-core/src/ai/proposal.rs`（新規）、`run.rs`（JSON の項目の読み方を共通に、`output: diff` を実行する）、`workspace.rs`（`adopt_proposals`、変更の知らせ `Proposals`）、`app/src-tauri`（`proposal_files`・`view_proposals`・`adopt_proposals`）、`app/src/ai/ProposalPanel.tsx`（新規）・`AiScreen.tsx`・`model.ts`、`App.tsx`、CSS、`docs/spec/project-files.md` の9節、作品フォルダの指示書（ひな形と両サンプル）。

## D070 生成と自律（2026-10-08）

- 決定：
  - 生成（`generate`）は、今のシーンがスタブのときだけ、本文の行（台詞・地の文・演出の命令）を差し込む（コアの `ai::generate`・`Workspace::write_draft`）。流れの行は書かず、今ある行は変えず、メタ情報の `status` だけを `ai-draft` にする。差し込んだ行にだけ行IDを付けて保存し、出自を `ai` と記録する。差し込むとシーンの辺が変わる下書きは書かない。シーンを足す生成（ルートの骨格）は、フロー図の AI 支援（T3-10）で作る。
  - 自律（`auto`）は、章のスタブを上から、展開メモ → 本文 → 点検（`check`：構文・意味・検証の段階1と表記の検査 I204〜I206 のうち下書きの範囲のもの、と指摘のタスク）→ 直す、を反復の上限まで繰り返し、シーンごとに1回だけ書き込む（`ai::run_auto`。呼び出しと書き込みは `AutoHost`）。点検と直しは作品の写しで、仮の行IDを付けて行う（直しの応答の仮の行IDは除いて読み、点検の結果の仮の行IDは書き込んだ行IDに付け替える）。応答はコードブロックがあればその中だけ、2つ目の見出しより前だけを読む。トークン数の上限と取り消しは、段（呼び出し）の合間ごとに見る。取り消したら、できている下書きも書かない。上限に達したら、できている下書きは書き、次の段を始めない（止めたことを返す）。
  - 大きな実行は Git のブランチで行う（コアの `gitops`。依存を足さずに `git` コマンドを呼ぶ）。保存していない変更・コミットしていない変更があれば、ブランチの上にいなければ（detached HEAD）始めない。走っている間は、人の本文の保存（と本文を書き換える操作）を止める（ブランチならどの章も、作品フォルダに直接なら書く章だけ）。自律は1つずつ。書いたら、書いたファイルと出自の記録だけをコミットして基のブランチに戻り、人が差分を見て取り込む（`--no-ff` のマージ。ぶつかれば取り込みをやめて元に戻す）か、確かめてから捨てる。何も書かなければブランチを消す。コミットできなければ、書いた分を失わないようにブランチにとどまる。Git でなければ作品フォルダに直接書く。`scn new` は `.gitattributes` に `ai/provenance.jsonl merge=union` を書く（取り込みで出自の記録がぶつからない）。
  - クラウドを使う自律は、送る項目と回数を見せて人が確かめてから（コアが確かめを求める）。
  - 書き出し（台本、プレーンテキスト、Ren'Py）と縦書きビューに「AI下書きを含める」（既定は含める）。切ると、AI下書きのシーンの台詞と地の文を省き、流れを残して省いたことを地の文で示す（コアの `ai::without_ai_drafts`。CLI `--no-ai-drafts`）。
- 理由：設計検討書「生成の進め方」（スタブと空きにだけ書く、`ai-draft`、上から下へ、生成後に点検して直す、トークン数と反復回数の上限、大きな実行はブランチで確認してから取り込む、プレビューとエクスポートでAI下書きを含めるかを選べる）と原則6（人の行は変えない）。展開メモをファイルに書かないのは、人の作ったスタブの構造（メタ情報）を変えないため。人が作ったスタブの `status` を書き換えるのは、AI が書いたことを示す状態だから（本文ではない）。
- 影響：`crates/scn-core/src/ai/generate.rs`・`auto.rs`・`gitops.rs`（新規）、`run.rs`（生成の実行）、`workspace.rs`（`write_draft`）、`line_id.rs`（`insert` をクレートの中で使う）、`context.rs`（`preamble`）、`scn-cli`（`--no-ai-drafts`）、`app/src-tauri`（`write_ai_draft`・`ai_auto`・`ai_branches` ほか、書き出しの `ai_drafts`）、`app/src/ai/AutoPanel.tsx`（新規）・`AiScreen.tsx`・`model.ts`、`App.tsx`、`export/ExportScreen.tsx`、`preview/VerticalView.tsx`、CSS、`docs/spec/project-files.md` の9節。

## D071 プロットとフローへのAI支援（2026-10-08）

- 決定：
  - 発散：提案ノード（`output: proposals`）は、1案ごとに「対象のシーンに足す選択肢1つ（`@設定` の行を付けてよい）と、その行き先（今あるシーンか、その案で足すスタブ）」とする。応答は `### 提案 N：案の名前` ごとに `.scn` の形で読む（コアの `ai::parse_branch_proposals`）。フロー図では、元のシーンの次の列に点線の仮ノードとして重ね（位置は保存しない）、文脈パネルの「AIの提案」で1案ずつ採用・却下する。採用（`Workspace::adopt_branch`）は、スタブを章の末尾に `status: ai-draft` で足し、選択肢をフロー図からの編集（T2-9、D060）と同じ規則で書き足して保存し、足した `@選択` と選択肢の行の出自を `ai` と記録し、足したシーンと元のシーンを検証の段階1で調べて見せる。
  - 生成（ルートの骨格）：`generate` で文脈に `scene` の無いタスクを、ルートの骨格を作るタスクとする（`ai::is_skeleton`。出力の形は足さない）。対象のルートと書く章（新しい章も）を選んで実行し、応答のシーンIDのある見出しごとに、メタ情報の `summary`・`route` と流れの行だけを読んで（`ai::parse_skeleton`）、章の末尾に `status: ai-draft` で足す（`Workspace::write_skeleton`）。シーンIDが重なる、行き先が無い、足した範囲に誤りが出るなら書かない。入口の辺は人がフロー図で引く。
  - レビュー：文脈の項目 `structure`（構造の検証の結果。ルートの分量、エンディングへの到達とその例、カバレッジ、結果が同じになる選択、流れと伏線の診断）を足し、`thin_branches` に入れる（キャラクターの欲求と葛藤も入れる）。どれもコアが計算したもの（`ai::structure_text`）。「結果が同じになる選択」は、どれを選んでも行き先と変数の書き込み（並べ替えて比べる）が同じ選択（中に分岐・呼び出し・エンディングのある選択肢は比べない）。
  - 同期：シーン要約のキャッシュ（本文の変わっていないもの）とメタ情報の `summary` が違うシーンを、提案と同じ「今／案」の文字の差分で見せ（`ai::summary_drift`。複数行の要約は1行にした案）、採用で `summary` の1行だけを書き換える（`Workspace::set_scene_summary`。書く前の本文が要約を作った本文と同じときだけ、書いた後の本文で要約のキャッシュを要約はそのままで書き直す）。章の要約をまとめて作り直せる（Tauri の `ai_summarize`。クラウドでは送るシーンの数を見せて確かめる）。
  - 問い返し：組み込みのタスク `concept_questions`（指摘の形）と `idea_sort`（新しい出力の形 `ideas`：メモの分類案）を足し、文脈の項目 `ideas`（アイデアメモの一覧）を足す。企画の画面の右端に「AIの問い返し」を置き、質問は「メモにする」でアイデアメモに、分類案は「当てる」でメモの状態とタグに書く。

  - 設計検討書の範囲（フェーズ3まで）の後に、フェーズ4（`docs/plan/phase4.md`）を足す。中身は、ローカルの LLM だけで一通りの AI の機能を使えるようにすること（タスクの接続先と文脈の長さを端末で選ぶ、考えるモデルの考えた中身を除く、OpenAI 互換の構造化出力）と、生成と自律が企画書と設定DBを書けるようにすること（企画書の下書き、設定の下書き、自律の前段と、章の後の未登録の話者の設定）。
  - 企画書と設定に AI が書いたことは、`ai/provenance.jsonl` に、ファイルと項目の形の記録で残す（項目ごとに `ai`・`ai-edited`）。AI が作ったエントリには `status: ai-draft` を書く。
  - 企画書と設定DBでも、原則6（AIは共作者）を守る：AI が直接書くのは空いている項目と AI が作るエントリだけで、人が書いた値への案は項目ごとの提案にする。
- 理由：人の相談と判断（2026-10-09）。H20 で LM Studio を試し、ローカルの LLM でも一通り動かしたい、「企画書とメモへの問い返し」などがクラウド専用になっている理由はあるか、自律や生成に企画と設定の作成を足したい、という相談に、調べた結果（クラウド専用はタスクの定義の既定の `model: cloud` だけで、コードの制限ではない。ローカルで常用するには3点が足りない。生成と自律が書けるのは `.scn` だけ）と案を示し、人が「3点＋構造化出力」「フェーズ4で全部作る」「ファイルと項目で記録」を選んだ。設計検討書の「上から下へ（企画 → スタブ → 展開メモ → 本文）」の一番上の段を埋める形になる。
- 影響：`docs/plan/phase4.md`（新規）、`docs/design.md` のロードマップ、`CLAUDE.md` と `README.md` の「現在のフェーズ」、`docs/progress.md`。仕様（`docs/spec/project-files.md` の2節・9節）は各タスクで先に書く。

## D083 返す分の上限を接続先ごとに上書きできるようにする（2026-10-09）

- 決定：フェーズ4に T4-10 を足す。接続先の設定に返す分の上限 `output_tokens` を足す（`project.toml` の `[ai.<名前>]` と端末の `ai.toml` の `[connections.<名前>]`。決め方は `context_tokens` と同じ）。書けば、文脈に使う上限を「文脈の長さ − 返す分の上限」にし、`max_tokens` を返す分の上限にする。書かなければ今と同じ（文脈の長さの4分の1、多くて4096）。返す分の上限が文脈の長さ以上なら実行しない。環境設定に欄を、`scn ai context` に `--output-tokens` を足す。
- 理由：人の報告（2026-10-09）。ローカルの考えるモデル（LM Studio、文脈の長さ 262144）で、考える分だけで返す分の 4096 トークンを使い切り、答えの無い誤りで止まった。文脈の長さを増やしても返す分は 4096 より増えず、誤りの文の直し方（文脈の長さを増やす）も当てはまらなかった。
- 影響：`ai::connection`（`Override`・`Connection`・`ConnectionStatus`）、`ai::context`（`TokenBudget`・`assemble`）、`ai::client`（誤りの文）、`project`（`[ai.<名前>]` の読み方）、Tauri の `set_ai_override` と文脈の組み立て、環境設定の画面、CLI の `ai context`、仕様の2節、`docs/guide/scn.md`。
