# フェーズ4 作業手順：ローカルのLLMと、企画・設定の生成

フェーズ4では、アプリの AI をローカルの LLM だけでも一通り使えるようにし（タスクの接続先と文脈の長さを端末で選ぶ、考えるモデルの考えた中身を除く、構造化出力）、生成と自律が企画書と設定DBも書けるようにする（企画書の下書き、設定の下書き、項目ごとの出自の記録、自律の前段）。設計検討書（`docs/design.md`）のロードマップはフェーズ3で終わる。このフェーズは、フェーズ3の人の確認（H20：LM Studio で試した）の後の、人の相談と判断（2026-10-09、D080）で足したもの。

状態：人の確認を除いて完了（2026-10-09、T4-7、D081。完了の判定は `docs/progress.md`、残りは `docs/review-for-human.md` の3節の Y1〜Y8）。以下は計画のときの文。人の指示（「確認したいことは推奨で進め、まとめておく」）により、このフェーズの中の判断は推奨案で決めて `docs/review-for-human.md` の1節に、人の環境でしか確かめられないことは2節に書く。

## 人の相談と判断（2026-10-09、D080）

- 相談：ローカルの LLM でも一通りの機能を動かしたい（「企画書とメモへの問い返し」などがクラウド専用になっている理由はあるか）。自律や生成に、企画と設定の作成を足したい。
- 調べたこと：クラウド専用にする仕組みはコードに無い。AIタスクの定義（`ai/<タスク>.yaml`）の既定の `model: cloud` だけで、設計検討書の「行単位のチェックはローカル、構成の提案やレビューはクラウド」の使い分けに沿った既定値。ローカルで常用するには、タスクの接続先を端末で選べない（定義は作品で共有するファイル）、考えるモデルの考えた中身（`<think>`）を除いていない（生成で本文に入るおそれ）、文脈の長さを端末で変えられない、の3つが足りない。生成と自律が書けるのは `.scn` だけで、企画書と設定DBへは問い返し（質問）と分類案と設定矛盾の指摘だけ。
- 人の判断：
  1. ローカルの LLM：足りない3点に、構造化出力（OpenAI 互換の `response_format`）を加えて作る。
  2. 企画と設定の作成：フェーズ4として全部作る（企画書の下書き、設定の下書き、自律の前段、自律の中での未登録の話者の設定）。
  3. 企画書と設定に AI が書いたことの記録：`ai/provenance.jsonl` に、ファイルと項目の形の記録を足す（項目ごとに `ai`・`ai-edited`）。AI が作ったエントリには `status: ai-draft` を付ける。

## 完了の条件

1. ローカルの LLM（OpenAI 互換。LM Studio・Ollama など）だけで、組み込みのすべてのタスク（指摘・提案・生成・自律、プロットとフローへの支援、企画書と設定の下書き）を、作品フォルダのファイルを書き換えずに、この端末の設定だけで実行できる。考えるモデルの考えた中身が、本文・指摘・要約・企画書・設定に入らない。
2. 企画書と設定の下書きを、生成（企画の画面・設定DBの画面・AI実行の画面）と自律（前段と、章の後の未登録の話者）から作れる。空いている項目にだけ書き、人が書いた値は変えずに提案として出る。AI が書いた項目の出自が記録され、人が直すと `ai-edited` になる。
3. 1と2を、模擬のサーバー（OpenAI 互換と Messages API）のテストで確かめている。`scripts/check-all` が成功する。
4. 人の確認（このフェーズで2節に足すもの）が済んでいる。人がローカルの LLM で、企画書と設定の下書きを作った。

## Claude Code（Opus 5.5）での進め方

フェーズ3と同じく、1タスクを1区切りとして `/phase-task` の手順（計画、テストを先に、実装、`scripts/check-all`、`plan-reviewer`、記録、コミット）で進める。

- AI のタスクは、自動のテストで実際の LLM を呼ばない。コアのテストは模擬のサーバーで確かめる（`tests/ai*.rs` の作り方）。
- 画面を作るタスクは、確認用のページ（Vite で画面だけを描く。コアの呼び出しは模擬）を内蔵ブラウザで開いて見た目を確かめてから、人の確認を2節に書く。確認用のページはコミットしない。

- 設計の原則6（AIは共作者）：企画書と設定DBでも、AI が直接書くのは空いている項目と AI が作るエントリだけ。人が書いた値への案は、項目ごとの提案として出し、人が採用する。
- 新しい依存は足さない（JSON Schema はコアで `serde_json` の値として組む）。

## T4-1 タスクの接続先と文脈の長さを端末で選ぶ

**目的**：作品フォルダのファイル（`ai/*.yaml`、`project.toml`）を書き換えずに、この端末でタスクごとの接続先と、接続先の文脈の長さを選べるようにする。

**手順**

1. 端末の設定（`ai.toml`）に、タスクごとの接続先の上書き（タスクの名前 → 接続先の名前）と、接続先ごとの文脈の長さの上書き（`[connections.<名前>]` の `context_tokens`）を足す。仕様（`docs/spec/project-files.md` の2節）を先に書く。
2. タスクの接続先の決め方（端末の上書き → タスクの `model` → 既定の接続先）を、Tauri の `task_connection` からコアに移す。AI実行の画面、ほかの画面からの実行（`QuickRun`）、自律と、その点検のタスク、同期（要約）のすべてで同じ決め方を使う。上書きの接続先が無い・解決できないときは、使うときに知らせる。
3. AI実行の画面のタスクの欄で、接続先を選べるようにする（「定義のまま（`cloud`）」と、作品の接続先）。環境設定の接続先に、文脈の長さの上書きの欄を足す。上書きがあるときは、タスクの一覧と環境設定に、そう見せる。
4. クラウドの接続先を選んだときは、今までどおり許可と送る中身の確かめを通す（端末で選んでも、確かめを省かない）。

**完了条件**

- [x] 決め方の順（端末の上書き、定義、既定）と、上書きした文脈の長さで文脈を組むことを、コアのテストで確かめている
- [x] 画面の判断（選べる接続先、上書きの見せ方）にテストがある
- [x] `scripts/check-all` が成功する
- [ ] 人がローカルの LLM で、定義が `cloud` のタスク（問い返しなど）を local に切り替えて実行した（H32）

## T4-2 考えるモデルと構造化出力

**目的**：考えるモデル（qwen3 など）と小さいモデルでも、指摘・要約・下書き・企画と設定の応答を正しく読めるようにする。

**手順**

1. 考えた中身を除く：応答の本文の `<think>…</think>`（閉じが無ければ終わりまで）を、読み取り（指摘、要約、提案、下書き、骨格、分類案）の前に除く。OpenAI 互換の `reasoning_content`（`reasoning`）の差分は本文に入れず、進み具合では「考えています」として見せる。考える分で長さの上限に当たり、本文が空のときは、そうと分かる知らせにする。
2. 構造化出力：接続先の設定に `structured_output`（OpenAI 互換だけ。`project.toml` の `[ai.<名前>]` と端末の上書き）を足す。真なら、JSON を返すタスク（指摘、メモの分類案、企画書と設定の下書き）に `response_format`（`json_schema`）を付けて送る。読み方は今の `parse_json_items`（`{"findings": [...]}` も読む）のまま。接続先が断ったら（400 など）、構造化出力を切るよう知らせる（推奨案で決める）。
3. 送る中身の見せ方（`test_preview`、送る前の確かめ）に、構造化出力を付けたことを出す。仕様を先に書く。

**完了条件**

- [x] 模擬のサーバーで、`<think>` の入った応答（ストリームの途中で分かれるものも）、`reasoning_content`、`response_format` を付けた依頼と応答、断られたときの知らせをテストで確かめている
- [x] `scripts/check-all` が成功する
- [ ] 人が考えるモデルで、指摘とスタブの下書きを作り、考えた中身が入らないことを確かめた（H33）

## T4-3 企画書と設定の出自（ファイルと項目）

**目的**：企画書（`concept.md`）と設定DBのエントリに AI が書いた項目を記録し、人が直したら `ai-edited` にする（D065 の行の記録と同じ考え方）。

**手順**

1. 記録の形を足す：`{"file": "<作品フォルダからのパス>", "key": "<項目>", "origin": …, "task": …, "model": …, "at": …}`。項目はフロントマターのキーと、本文（決め方は推奨案で決める）。行の記録と同じ `ai/provenance.jsonl` に書き足す。読むときは行の形か項目の形として読み、どちらでもない行は今までどおり読めない行にする。仕様（9節）を先に書く。
2. 人が直したら `ai-edited`：アプリのフォーム（企画の画面、設定DBの画面）とソース表示の保存で、AI の項目の値が変わったら書き足す。外部のエディタの変更は数えない（行と同じ）。ファイルの名前が変わったとき（エントリの「IDを変える」）は、記録のファイルも書き足しで移す。
3. AI が作ったエントリには、フロントマターに `status: ai-draft` を書く（設定DBの画面で見分け、人が消せば確定）。
4. 一覧と書き出し：`scn provenance` とアプリの「出力」の AI の一覧に、項目の記録を足す（CSV にファイルと項目の欄）。
5. 企画の画面と設定DBの画面で、AI が書いた項目に印を付ける（エディタと同じく、`ai` は実線、`ai-edited` は点線。色だけで分けない）。

**完了条件**

- [x] 項目の記録の読み書き、フォームとソース表示の保存での `ai-edited`、IDを変えたときの移し、一覧と CSV をテストで確かめている
- [x] 画面の印の判断にテストがある
- [x] `scripts/check-all` が成功する
- [ ] 人が印の見た目を確かめた（H34）

## T4-4 企画書の下書き

**目的**：アイデアメモと今の企画書から、企画書の空いている項目を AI が下書きし、人の書いた項目への案は提案として出す。

**手順**

1. 新しい出力の形（企画書の下書き）と、ひな形とサンプルのタスク（`ai/draft_concept.yaml`。文脈は企画書、メモ、キャラクター、文体）。応答は JSON の対応表（`logline`・`theme`・`tone`・`volume`・`main_characters`・`endings`・本文）。仕様（9節のタスクの定義と、生成の書き込み）を先に書く。
2. 書き込み：空いている項目にだけ、今の書き換え（直したキーの行だけ）で書き、項目ごとに出自を記録する。`endings` は無い・空のときだけ書く。本文は、空か、ひな形のままのときだけ書く（推奨案で決める）。企画書が無ければ、ひな形で作ってから書く。
3. 人の書いた項目への案は、項目ごとの提案（今・案）にして、企画の画面で採用・却下する。採用は同じ書き換えで書き、出自を `ai` と記録する。
4. 企画の画面に「AIで下書き」（ほかの画面からの実行と同じ。クラウドでは送る中身を確かめる）と、書いた項目・提案の一覧を足す。AI実行の画面からも実行できる。

**完了条件**

- [x] 模擬のサーバーで、空いている項目だけに書くこと、人の項目が変わらないこと、提案の採用、出自、企画書の無い作品をテストで確かめている
- [x] `scripts/check-all` が成功する

**完了条件**

## T4-9 設定DBの既定の型とテンプレート集（人の追加の頼み。D082）

**目的**：設定DBの型を一から作らなくてよいように、既定の型を充実させ（キャラクターの役割など）、物語の設定に関わる型（場所、組織、アイテム、用語、出来事、世界観の決まり、関係、伏線、種族、能力、文化など）を最初から置き（要らなければ消す）、型のテンプレート集と、今ある型の複製から新しい型を作れるようにする。

**手順**

1. 型のテンプレート集をコアに置く（`templates/types/*.yaml` を埋め込む。名前、説明、項目）。キャラクターの型は項目を充実させる（役割、読み、二人称、口癖、年齢、外見、性格、好き嫌い、欲求と本当に必要なもの、秘密、生い立ち、変化、所属、住まい、関わりの深い人物、初登場、イメージカラー、声優と演技メモなど）。仕様（`docs/spec/project-files.md` の5節）を先に書く。
2. `scn new` がテンプレート集の型（汎用を除く）を作品フォルダに置く。サンプルは変えない。
3. 型を作るとき（アプリの「＋ 型」）に、元にするものを選べるようにする：空の型、テンプレート集の型、今ある型（複製。項目ごと写し、名前を変える。元とはつながらない。`builtin` は写さない）。書くのはコア。
4. 設定DBの画面の「＋ 型」の欄に、元にするものの選択（テンプレートの説明つき）を足す。

**完了条件**

- [x] テンプレート集のすべての型が誤りなく読めること、`scn new` の作品が読み込みの診断を出さないこと、テンプレートと複製から型を作れること（名前の差し替え、`builtin` を写さない、使われているIDは断る）をテストで確かめている
- [x] 画面の判断にテストがある
- [x] `scripts/check-all` が成功する
- [ ] 人が設定DBの画面で、テンプレートと複製から型を作った（H39。待ち）
