# フェーズ0 作業手順：形式を固める

フェーズ0では、`.scn` 形式をv0として確定し、それを読むパーサとIR、ハイライト、アプリの土台を作る。最後に、WindowsとmacOSで日本語入力に問題がないことを確かめる。

## ゲート（フェーズ1へ進む条件）

1. `samples/houkago/` を解析でき、分岐（選択肢・条件分岐・ジャンプ）を含むIRが出る。意図して残した診断（仕様書の付録とサンプルの約束を参照）以外のエラーが無い。
2. WindowsとmacOSで、`docs/plan/ime-test.md` の必須項目がすべて合格する。

## タスクの流れ

```
T0-1 土台 ─▶ T0-2 仕様確定 ─▶ T0-3 構文解析 ─▶ T0-4 意味解析・IR ─▶ T0-5 開発用CLI
                    │                                   │
                    └──────▶ T0-6 Lezer文法 ─────────────┴─▶ T0-7 アプリの土台 ─▶ T0-8 IMEテスト ─▶ T0-9 ゲート判定
```

T0-6は、T0-2が終われば、T0-3〜T0-5と並行して進められる（別のセッション、またはworktreeで）。

## Claude Code（Opus 5.5）での進め方

### 最初の準備

1. ZIPを展開し、フォルダで `git init` と最初のコミットを行う。
2. RustとNode.jsとpnpm、TauriのOS別の前提ソフトを入れる。バージョンは各公式の最新の安定版にする（Tauriの前提ソフトは公式ドキュメントの「Prerequisites」に従う）。
3. フォルダで `claude` を起動し、`/model` でOpus 5.5を選ぶ。
4. `/permissions` で、`cargo`・`pnpm`・`git` のよく使うコマンドを許可しておくと、長いタスクの途中で止まりにくい。

### 1タスクの回し方

- 1タスクを1セッションで扱う。タスクが終わったら `/clear` してから次へ進む。前回の状況は `docs/progress.md` から引き継がれる。
- 依頼は `/phase-task T0-3` のように出す。調査、計画、実装、検証、レビュー、記録、コミットまでを一通り行う手順になっている（`.claude/skills/phase-task/`）。
- 設計判断を含むタスク（T0-2、T0-4、T0-7）は、計画が出た時点で目を通し、方向がずれていれば早めに直す。
- 長いタスク（T0-3、T0-4）では、完了条件のコマンドが成功することを `/goal` に設定しておくと、途中で止まりにくい。
- 終わったら、報告に書かれたコマンドと結果を見る。気になる点は同じセッションで直させる。2回直しても合わなければ、`/clear` して依頼を書き直す。

## T0-1 リポジトリの土台と検査コマンド

**目的**：以降のすべてのタスクを、同じ検査コマンドで確かめられるようにする。

**手順**

1. Cargoのワークスペースを作る。メンバーは `crates/scn-core` と `crates/scn-cli`。`rust-toolchain.toml` で安定版に固定し、editionは最新の安定版にする。`app/src-tauri` はT0-7で加える。
2. pnpmのワークスペースを作る（`pnpm-workspace.yaml` に `packages/*` と `app`）。中身はT0-6とT0-7で作るので、この時点では空でよい。
3. 書式と静的検査をそろえる。Rustは `rustfmt` と `clippy`。TypeScriptは、整形と検査を1つで済ませられるツール（Biomeなど）を選び、理由を `docs/progress.md` に書く。
4. `scripts/check-all`（macOS用のシェルスクリプト）と `scripts/check-all.ps1`（Windows用）を作る。中身は、書式の確認、clippy、Rustのテスト、存在するパッケージの型検査・静的検査・テスト。
5. `CLAUDE.md` の「コマンド」の節を、実際に動くコマンドだけに書き直す。

**成果物**：`Cargo.toml`、`rust-toolchain.toml`、`rustfmt.toml`、`package.json`、`pnpm-workspace.yaml`、`scripts/check-all`、`scripts/check-all.ps1`、ビルドの通る最小の2クレート。

**完了条件**

- [ ] `scripts/check-all` が成功する（Windowsでは `scripts/check-all.ps1`）
- [ ] `CLAUDE.md` のコマンドの節に、存在しないコマンドが残っていない

**やらないこと**：CI（GitHub Actionsなど）の設定。フェーズ1で検討する。

## T0-3 scn-core：行の分類と構文解析

**目的**：設定DBに依存しない構文解析を作る。対象は、行の分類、行IDの切り出し、シーン見出しとメタ情報、ブロック（選択・分岐・生コード）、文中の記法、式。エラー回復を含む。

**手順**

1. fixtureを先に作り（T0-2の一覧のうち構文系）、`insta` のスナップショットテストの枠を作る。
2. `line`、`syntax`、`inline`、`expr` の順に実装する（構成は `.claude/rules/rust.md`）。
3. エラー回復を入れる。例えば、閉じていないブロックはシーン見出しの位置で閉じたものとみなす。閉じていない台詞は、空行やディレクティブの手前で終える。
4. 任意の入力でパニックしないことを、`proptest` で確かめる。
5. `samples/houkago/story/*.scn` を構文解析し、結果のスナップショットを読んで確認する。

**完了条件**

- [ ] `cargo test -p scn-core` が成功する
- [ ] 段階0の構文系の診断（W101、E102〜E106、W107、I109、E110、E111、W112、W113、E114、E201、W303、E304、W401、E402、W405、E601）に、それぞれfixtureとテストがある（一覧は `crates/scn-core/tests/fixtures/README.md`）
- [ ] `samples/houkago/story/*.scn` の構文解析で、エラー（E）が0件
- [ ] proptestのテストがあり、成功する
- [ ] `cargo clippy --workspace --all-targets -- -D warnings` が成功する

**やらないこと**：設定DBとの照合（T0-4）、行IDの付与（フェーズ1）、差分更新（フェーズ1）。

## T0-4 scn-core：プロジェクト読み込み、意味解析、IR

**目的**：プロジェクトフォルダを読み込み、話者・参照・変数を確かめ、IRを作る。

**手順**

1. `project` モジュールで、`project.toml`、設定DBのキャラクター（型定義とエントリ）、`variables.yaml`、`assets/catalog.yaml`、`story/*.scn` を読む。設定DBの他の型は、読み込めることを確かめる程度でよい。
2. `sema` で、話者の解決、変数の名前空間の正規化、変数の型の検査、ジャンプ先の存在、シーンIDと行IDのプロジェクト全体での重複、素材の意味名の照合を行う。
3. `ir` で、シーンごとの命令列と、シーン間の辺を作る。`serde` でJSONにし、`ir_version` を持たせる。
4. 仕様書の「17. IRの形」を、実装した形に合わせて更新する。
5. `criterion` で、1万行の合成データの解析時間を測り、結果を `docs/progress.md` に書く。

**完了条件**

- [ ] `samples/houkago/` 全体のIRのスナップショットがある。人が中身を見て、話者（灯→`akari`）、変数（`灯.好感度`→`akari.好感度`）、選択肢、条件分岐、辺、エンディングが期待どおりか確認した
- [ ] 段階0の意味系の診断（E108、W202、E301、I302、I403、W404、E501、W502、W602、E603、E604）に、それぞれfixtureとテストがある（一覧は `crates/scn-core/tests/fixtures/README.md`）
- [ ] サンプル全体のエラー（E）が0件。警告と情報は、意図して残したものだけ
- [ ] ベンチマークの結果が記録されている（目安：1万行を100ミリ秒以内）
- [ ] `scripts/check-all` が成功する

**人の作業**：IRのスナップショットを読み、形と命名に違和感がないかを見る。

## T0-5 開発用CLI `scn`

**目的**：コアを、ターミナルとAIエージェントから使えるようにする。フェーズ0では開発用の2コマンドだけを作る。

**手順**

1. `crates/scn-cli` に `clap` でCLIを作る。
2. `scn parse <file.scn>`：構文解析と（プロジェクト内なら）意味解析を行い、診断を `ファイル:行:列 コード メッセージ` の形で出す。`--json` で診断をJSONで出す。
3. `scn ir <project-dir>`：プロジェクト全体のIRを、標準出力にJSONで出す。
4. 終了コードは、成功が0、エラー（E）の診断があれば1、使い方や入出力の誤りは2。
5. `assert_cmd` で、サンプルとfixtureを使った端から端までのテストを書く。

**完了条件**

- [ ] `cargo run -p scn-cli -- ir samples/houkago` がJSONを出し、終了コード0で終わる
- [ ] エラーを含むfixtureで、`scn parse` が期待した診断と終了コード1を返す
- [ ] CLIのテストが `scripts/check-all` に含まれ、成功する
- [ ] `CLAUDE.md` のコマンドの節と、`samples/houkago/CLAUDE.template.md` の検証の手順が、実際のコマンドに合っている

**やらないこと**：`check`・`graph`・`fmt`（フェーズ1）。

## T0-6 Lezer文法とハイライト

**目的**：エディタのハイライト用に、`.scn` のLezer文法を作る。

**手順**

1. `packages/lezer-scn` を作り、`@lezer/generator` で文法を書く。トークン名は `docs/glossary.md` の英語名に合わせる。
2. 行の種類、行ID、文中の記法（ルビ、傍点、インライン命令、変数の埋め込み）、ディレクティブ名、式の演算子を見分けられるようにする。
3. 壊れた入力でも、次の行から正しい状態に戻るようにする。
4. CodeMirror 6の言語サポート（`LanguageSupport`）として書き出し、ハイライトのスタイル対応を用意する。
5. `samples/houkago/story/*.scn` を入力に、各行が意図した種類のトークンになるかをテストする。

**完了条件**

- [ ] `pnpm -C packages/lezer-scn test` が成功する
- [ ] サンプルの全行について、行の種類の判定がテストで確かめられている
- [ ] 閉じていないブロックや括弧を含む入力でも、後続の行のハイライトが崩れないことをテストで確かめている

## T0-7 Tauri＋Reactの土台

**目的**：Tauri、React、CodeMirror 6、xyflow、Rustコアを、最小の画面で通しで動かす。見た目の作り込みはしない。

**手順**

1. `app/` に、Tauri 2、React、TypeScript、Viteの構成を作る。作り方はTauri公式の最新の手順に従う。`app/src-tauri` をCargoのワークスペースに加える。
2. Tauriのコマンドを2つ作る。`open_project(path)` はIRと診断を返し、`parse_buffer(file, text)` は保存していない編集中のテキストの診断を返す。
3. 画面を作る。左にシーンの一覧（IRから）、中央にCodeMirrorのエディタ（`lezer-scn` でハイライト、診断に下線）、右にxyflowのシーンのグラフ（自動配置）を置く。
4. 日本語入力の変換中は、解析の依頼、補完、括弧の自動補完を行わない（`.claude/rules/frontend.md`）。
5. UTF-8のバイト位置とUTF-16の位置の変換関数を作り、全角文字とサロゲートペアを含むテストを付ける。
6. `docs/ui/README.md` のデザイントークンをCSS変数にする。
7. 開発用に、起動時に `samples/houkago` を開く設定を用意する（IMEテストのため）。

**完了条件**

- [ ] `pnpm -C app tauri dev` で起動し、サンプルを開ける
- [ ] 本文を編集すると、入力が止まってから診断とグラフが更新される
- [ ] 位置の変換関数のテストが成功する
- [ ] `scripts/check-all` が成功する
- [ ] 人がWindowsとmacOSで起動し、上の2点を確かめた

**やらないこと**：執筆表示（チップ表示）、保存、ファイル監視、フロー図の座標の保存、プレビュー、設定DBの画面。すべてフェーズ1以降。
