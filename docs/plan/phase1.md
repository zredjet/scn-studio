# フェーズ1 作業手順：執筆の核

フェーズ1では、`.scn` で分岐のある短編を書き切るための道具をそろえる。エディタ（執筆表示・ソース表示、入力補助）、保存と外部の変更の取り込み、検証の段階1と `scn check`、構造グラフ、設定DBと変数の画面、簡易ADVプレビュー、台本の出力を作る。Claude Codeが作品フォルダで書いて検証できるよう、CLIと作品フォルダの用意（`FORMAT.md`・`CLAUDE.md`）も整える。

状態：確定（2026-10-07、T0-9で人が確認した）。フェーズ0の記録（`docs/progress.md`）と `docs/design.md` のロードマップから作った。線引きの理由は D040。

## T1-2 仕様の積み残しと行IDの付与（`scn fmt`）

**目的**：フェーズ0で残した仕様の判断を片づけ、行IDを付ける仕組みをコアとCLIに作る。行IDは、保存（T1-6）、台本（T1-12）、AIの出自の記録が頼るので、早く固める。

**手順**

1. 閉じ括弧の後ろが記法だけの台詞（`灯「またね」{p}`）を、台詞にするか地の文にするかを、人に確認する。決めたら仕様書の6節、コア、Lezer文法、fixtureを合わせる。
2. 行IDの付与を、仕様書9節の「付与のきまり」に沿って、コアの関数として作る（6文字の乱数、プロジェクト全体で重ならない）。付けるのは行の末尾だけで、ほかの文字は1バイトも変えない（改行の `\r\n`、全角空白、BOMを保つ）。
3. `scn fmt <project-dir>` を作る。行IDの無い行に行IDを付ける。`--check` では書き換えずに、付ける行があれば終了コード1を返す。整形（字下げや空白の調整）はしない。
4. 次のことを人に確認して決める。
   - どの行に付けるか（`ai-draft` のシーンの行にも付けるか）
   - 外部のAIエージェント（Claude Codeなど）が書いた行を、`ai/provenance.jsonl` にどう記録するか（「フェーズ1へ」から）。フェーズ1では、きまりを決めて仕様と `CLAUDE.template.md` に書くところまでにする。記録を自動で書く仕組みは、出自の記録としてフェーズ3で作る
5. 行の分割と結合のきまり（前半が元のIDを引き継ぐ、など）は、エディタの操作なのでT1-8で作る。

**完了条件**

- [ ] `灯「またね」{p}` の扱いが決まり、仕様書・コア・Lezer文法・fixtureがそろっている
- [ ] 行IDの付与に、fixtureとテストがある。付与の前後で、行IDを足した部分以外のバイトが変わらないことを、proptestで確かめている
- [ ] `scn fmt` を2回続けて実行しても、2回目は何も変えない（テストで確かめる）
- [ ] `samples/houkago` の写しに `scn fmt` を実行すると、手順4で決めたきまりに当たる行にだけ行IDが付き、ほかのバイトは変わらない（I302の5行はどれも `ai-draft` のシーンにあるので、`ai-draft` にも付けると決めた場合は、その5行に付く）
- [ ] 手順4で決めたことが `docs/decisions.md` に記録されている
- [ ] `scripts/check-all` が成功する

**やらないこと**：エディタでの付与（T1-6、T1-8）、行IDの再採番。

## T1-3 索引、設定ファイルの診断、性能の測定

**目的**：エディタの補完、設定DBの逆引き、検証が共通に使う索引をコアに作る。設定ファイルが壊れていても解析を続けられるようにする。

**手順**

1. 索引を作る。シーン（ID、見出し、ファイル、ルート、状態、スタブか）、話者とキャラクターの出現箇所、変数の読み書きの箇所、素材の意味名の使用箇所、行IDの位置。IRと同じくJSONにできるようにする。
2. 設定ファイル（`project.toml`、`variables.yaml`、`assets/catalog.yaml`、設定DB）の誤りを、読み込みのエラーで止めず、診断にして解析を続ける（D036を改める。「フェーズ1へ」から）。新しい診断コードは人に確認し、仕様書の診断表とfixtureに足す。CLIの終了コード2（設定ファイルが読めない）の説明が変わるので、`CLAUDE.md` のコマンドの節、`samples/houkago/CLAUDE.template.md`、決定（D037を改める新しい決定）を合わせる。
3. 設定DBの読み込みを、型定義（`bible/types/*.yaml`）にもとづく一般の形にする。キャラクターは型定義の `builtin: character` で見分ける（「フェーズ1へ」から）。
4. 大きな合成データ（目安：10万行・数千シーン）で、解析・JSONへの直列化・アプリへの受け渡しにかかる時間を測る。打鍵ごとの再解析が遅すぎる（目安：50ミリ秒を超える）ときだけ、ファイル単位の差分更新を作る。測った結果を `docs/progress.md` に書く。

**完了条件**

- [ ] 索引のスナップショット（`samples/houkago`）がある。人が中身を見た
- [ ] 壊れた `variables.yaml` や設定DBのエントリがあっても、本文の解析が続き、診断が出る（fixtureとテスト）
- [ ] CLIの終了コードの説明（`CLAUDE.md`、`CLAUDE.template.md`、決定の記録）が、実際の動きに合っている
- [ ] 性能の測定結果が記録され、差分更新を作るかどうかの判断が書かれている
- [ ] `scripts/check-all` が成功する

## T1-4 検証の段階1と `scn check`

**目的**：`docs/design.md` の検証項目のうち段階1を、プロジェクト全体の検証として作り、CLIとアプリとAIエージェントが同じ検証を使えるようにする。

**手順**

1. 段階1の検証を作る。
   - 開始シーンから到達できないシーン
   - 行き止まり（W503。仕様書16節：シーンの終わりに出口が無い経路がある）
   - 書き込むだけで読まれない変数、読まれるのに一度も書かれない変数
   - メッセージウィンドウからのはみ出し（`project.toml` の `[message_window]`）
   - 企画書のエンディングと本文の `@エンディング` の食い違い（W701、W702）
   - 回収シーンの無い伏線
2. 新しい診断コードと、はみ出しの数え方（ルビ、記法、`{p}`、複数行の台詞）は人に確認して決め、仕様書の診断表と該当節に足す。エンディングに着かない循環（`s1 → s2 → s1`）を W503 に含めるか、別のコードにするかも人に確認する（`docs/design.md` の「どのエンディングにも続かない行き止まり」との違い）。fixtureを先に作る。
3. 企画書（`concept.md`）のフロントマターを読む。読む項目と形を仕様にする（企画書とメモの規約。T1-5で文書にまとめる）。
4. `scn check [project-dir]` を作る。診断を `ファイル:行:列 コード メッセージ` の形で、行IDがあれば添えて出す。`--json` でJSON。終了コードは `parse` と同じ。
5. CLIの解析を、アプリと同じく大きなスタックのスレッドで行う（Windowsのメインスレッドは1MB。T0-7の残り）。
6. 全角記号の誤入力（`＠背景`、`－＞` など）を見つける診断を足すかを、人に確認する（「フェーズ1へ」から）。
7. `samples/houkago/README.md` の「意図して残している診断」を、出るようになったものに合わせて更新する。

**完了条件**

- [ ] `scn check samples/houkago` が、`samples/houkago/README.md` で「フェーズ1以降の検証で出る予定」とした段階1の診断（`s014` の W503、`true_end` の W701、`s012` の `^k3ff` のはみ出し）を出す。それ以外に出た診断は、理由を書いて人が確かめ、README の「意図して残している診断」に足した

- [ ] `scripts/check-all` が成功する

## T1-5 `scn graph` と作品フォルダの用意

**目的**：Claude Codeが、新しい作品フォルダで、形式の仕様を読み、書き、検証できるようにする。

**手順**

1. `scn graph [project-dir]` を作る。シーン、辺、条件、変数の読み書きを一覧で出す。粒度（ルート・章・シーン）を選べる。`--json` でJSON。
2. 企画書（`concept.md`）、文体（`style.md`）、アイデアメモ（`ideas/`）の規約（ファイルの置き場所、フロントマターの項目）を、仕様として文書にまとめる。置き場所（仕様書の節か、別の文書か）は人に確認する。
3. 作品フォルダを新しく作るコマンドを作る（例：`scn new <dir>`。名前は人に確認する）。`project.toml`、`story/`、`bible/types/character.yaml`、`variables.yaml`、`concept.md`、`style.md`、`CLAUDE.md`、`FORMAT.md` を置く。アプリの「新しく作る」（T1-6）も同じコアの関数を使う。
4. `FORMAT.md`（作品フォルダに置く形式の仕様）の作り方を決める。仕様書から作る範囲（IRの節や決定の経緯は入れない、など）と、更新の方法を人に確認する。
5. `samples/houkago/CLAUDE.template.md` を、`scn check`・`scn fmt`・`scn graph` を使う手順に書き直す。WindowsのPowerShellでもそのまま動く手順にする（今の `scn ir . > /dev/null` は動かない）。新しく作る作品の `CLAUDE.md` も、同じひな形から作る。

**完了条件**

- [ ] `scn graph samples/houkago` が、粒度ごとに期待した一覧を出す（テスト）
- [ ] 新しく作った作品フォルダで、`scn check` がエラー0件で終わる（テスト）
- [ ] 企画書・文体・メモの規約が文書になり、人が確認した
- [ ] `CLAUDE.md` のコマンドの節と、`CLAUDE.template.md` の手順が、実際のコマンドに合っている
- [ ] `scripts/check-all` が成功する

## T1-6 アプリの骨格、開く・作る・保存、外部の変更の取り込み

**目的**：アプリで作品を開いて書き、保存できるようにする。Claude Codeが同じフォルダを書き換えても、アプリが追いつくようにする。

**手順**

1. 画面の骨格を `docs/ui/README.md` に合わせて作る。タイトルバー、左端のバー（フェーズ1で作る画面だけ：本文・フロー・設定・変数・検証・出力）、一覧パネル、作業領域、文脈パネル、ステータスバー。検証の画面は、プロジェクト全体の診断の一覧にし、選ぶとその行へ移る。
2. 作品フォルダを開く（フォルダを選ぶダイアログ）、新しく作る（T1-5の関数）、最近開いたものを開く。
3. 保存（Ctrl+S／Cmd+S）をコアのコマンドで作る。書いたとおりのバイトで保存する（改行、BOM、全角空白を保つ）。保存のときに行IDを付けるか、付けるならどの行に付けるかは、T1-2の決定に沿って人に確認する。保存していない変更があるときは、閉じる前に確かめる。
4. ファイルの監視（`notify`）。外部で変わったファイルは、保存していない変更が無ければ読み込み直す。保存していない変更があれば、「読み込み直す」か「自分の変更を残す」かを選ばせる（マージの画面はフェーズ2）。
5. `story/` に章（`.scn`）を足す操作を作る。
6. CSPを設定する（D039の残り）。

**完了条件**

- [ ] 保存の前後で、編集していない部分のバイトが変わらないことをテストで確かめている（CRLF、BOM、全角空白、絵文字を含む）
- [ ] 外部の変更の取り込みのテスト（保存していない変更がある場合と無い場合）がある
- [ ] 人がmacOSで、開く・作る・保存・外部での変更（Claude Codeでの書き換え）の取り込みを確かめた
- [ ] CSPが設定され、設定したうえでアプリが動く（開く・保存・グラフの表示）
- [ ] `scripts/check-all` が成功する

**やらないこと**：マージの画面、章の名前の変更と削除、`story/` のサブディレクトリ（フェーズ2）。

## T1-7 エディタ：執筆表示とソース表示

**目的**：同じテキストを、記号を畳んだ執筆表示と、生のソース表示で切り替えられるようにする。

**手順**

1. 執筆表示を作る。ディレクティブは小さなチップに畳み、行IDは隠し、ルビは本文の上に描く。カーソルのある行だけ生のテキストに戻す。見た目は `docs/ui/mockups/02-editor.html` に合わせる。
2. ソース表示は、生のテキストを出し、行IDを薄い色で出す（`02b-editor-source.html`）。
3. 切り替えはショートカット1つで行い、ファイルごとの表示を覚える。覚えておく場所は、作品のテキストを汚さないところにする（人に確認）。
4. 変換中は、畳み方や飾りを変えない（`.claude/rules/frontend.md`）。変換中の行の飾りが動かないことを、テストで確かめる。
5. 書体を同梱するか、OSの書体を使うかを人に確認する（D039の残り）。フォーカス中の選択の色がテーマの指定どおりにならない件（「フェーズ1へ」から）も、ここで直す。
